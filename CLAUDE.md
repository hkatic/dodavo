# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dodavo is a Windows-only Rust app (classic Win32 UI) for sending files and folders directly between computers over [iroh](https://iroh.computer). Peers are identified by a permanent **Contact ID** (the iroh public key), not an IP address. See README.md for the user-facing feature list.

## Commands

- Build: `cargo build --release` → `target\release\Dodavo.exe`. Needs the MSVC toolchain and Windows SDK (`rc.exe`); `build.rs` embeds `res/app.rc` and `res/app.ico` via `embed-resource`, with `res/app.manifest` as a template (`@VERSION@`) and the values of the version resource in a generated `app-info.h`, both written to `OUT_DIR`. `.cargo/config.toml` links the C runtime statically for every target. 32-bit: `cargo build --target i686-pc-windows-msvc`.
- Installer: `powershell -ExecutionPolicy Bypass -File installer\build.ps1` → `target\installer\Dodavo-<version>-setup.exe` + `.sha256`. Needs Inno Setup 6.6+ (32-bit edition). It builds four programs: x64 and x86 with stable Rust for Windows 10+, and x64 and x86 for Windows 7 SP1–8.1 with the Tier 3 `*-win7-windows-msvc` targets on a nightly pinned in `build.ps1` (`-Zbuild-std`, own `target\win7` dir). `-SkipWin7` builds a Windows 10-only installer. Setup picks the build by Windows version and install mode (`[Files]` in `Dodavo.iss`). Signs with signtool when `DODAVO_SIGN_THUMBPRINT` or `DODAVO_SIGN_PFX` is set (see README). Version, author (`authors`), website (`repository`) and copyright years (`[package.metadata.dodavo] copyright-years`) exist only in `Cargo.toml`: `build.rs` passes them to the program (`ui::COPYRIGHT_YEARS` via `DODAVO_COPYRIGHT_YEARS`), the manifest and the version resource (`CompanyName`, `LegalCopyright`, a custom `Website`), and `Dodavo.iss` reads publisher, copyright and URLs from that version resource. `README.md` repeats the copyright line; `about::tests` checks it. `build.ps1` stages the license files with CRLF line ends and a BOM for Setup (`LicenseFile`, `ThirdPartyLicensesFile`).
- Third-party licenses: `powershell -ExecutionPolicy Bypass -File installer\licenses.ps1` regenerates `res\third-party-licenses.txt` with cargo-about (`cargo install cargo-about --locked --features cli`; config `installer\about.toml`, template `installer\about.hbs`), plus a section for the Rust standard library from the `COPYRIGHT-library.html` of the active toolchain and the win7 nightly (its crates: std's closure in rust-src's `library\Cargo.lock` that the toolchain ships as `.rlib` for the host; installs rust-src). It writes the file only when the text changes (cargo rebuilds on its mtime). `build.ps1` runs it first. Run it after adding or updating dependencies or toolchains and commit the file with `Cargo.lock`; a new license must be GPL-3.0-compatible before it goes into `accepted`.
- Publish: `powershell -ExecutionPolicy Bypass -File installer\publish.ps1 [-Publish]` writes and verifies `target\installer\update.json` (the signed update manifest) from the built installer, `release-notes\<version>\<lang>.txt` and the secret key in `DODAVO_UPDATE_KEY_FILE`, and with `-Publish` creates the GitHub release `v<version>` through `gh`. The release tool behind it: `cargo build --release --features release-tool --bin dodavo-release` (`keygen`, `manifest`, `verify`). The private release guide lives outside the repo (`C:\Users\hrvoj\Documents\Dodavo-release\RELEASING.md`).
- Import check: `powershell -ExecutionPolicy Bypass -File installer\check-imports.ps1 <exe> [-Profile win7]` fails when an exe imports a DLL or function newer than its Windows baseline. `build.ps1` runs it on every build; run it after touching Win32 calls or dependencies.
- Test everything: `cargo test`
- Single test: `cargo test <name>`, e.g. `cargo test end_to_end` or `cargo test archive::`
- `net::tests::end_to_end`, `resume_after_disconnect`, `resume_after_restart`, `finish_alone_after_restart_during_unpacking`, `a_cancel_waits_for_the_verdict_across_a_restart` and `a_send_needs_its_data_again_when_the_receiver_lacks_it` start two real iroh endpoints in one process and need internet access (address lookup / relays). Run them with `--test-threads=1`; each can take a minute or two.
- Run two instances side by side: `Dodavo.exe --profile alice` and `Dodavo.exe --profile bob` (separate identity and settings). `--minimized` starts in the tray.
- Update testing: `DODAVO_UPDATE_URL` overrides the manifest URL (a local `python -m http.server` works) and `DODAVO_UPDATE_KEY` the trusted public keys (hex). `--updated` is what Setup starts the program with after an update.
- Force theme for testing: set `DODAVO_THEME=dark` or `DODAVO_THEME=light`. Force language: `DODAVO_LANG=en|hr|sr-Latn|sl`. `DODAVO_LEGACY_DPI=1` uses the Windows 7/8 DPI code path (system DPI only) on a current Windows.
- Debug builds keep a console window; release builds use the `windows` subsystem. A panic hook shows a message box: after a panic on the UI thread or in the network thread's own loop the program ends; one on another thread shows it from a thread of its own (one at a time), and the program goes on: a transfer whose task panicked fails with "An unexpected error occurred", its leftovers are deleted and the peer is told that it failed, unless it had ended already, which then stands: one that had completed (a received item in place) is reported as completed (`net::guarded`, `Session::ended`; the last step of a receive passes a panic on to it, `receive::Receiver::finalize`).

## Architecture

Two threads that never share UI state:

1. **UI thread** (`main.rs` message loop): owns all windows and the `App` state in `app.rs`, stored in a `thread_local!`. Access it only through `app::with(|a| …)`; do not create windows or show message boxes inside that closure, because they run nested message loops and would re-borrow the `RefCell`.
2. **Network thread** (`net::start`): a tokio multi-thread runtime that owns the iroh `Endpoint`.

They communicate in two directions:
- UI → net: `net::Command` (`Send`, `Respond`, `Cancel`) over an unbounded mpsc channel (`app::net_send`).
- net → UI: `net::Event` is pushed by `app::event_sink` into a global `EVENTS` queue (as `app::Queued::Net`; the update thread pushes `update::Event` through `app::update_sink` as `Queued::Update`), which then posts `WM_APP_NET` to the main window. `app::process_events` drains the queue on the UI thread. If a target window is busy (for example, a modal message box is open), the handler returns the event, which is requeued and retried after 250 ms by a timer. Keep that contract when adding events. `Progress` events may be dropped; the others must not be.

Transfer ids come from `net::next_transfer_id()` and are used in both directions (restored transfers get fresh ids). `App.transfers` maps id to progress window, and `App.offers` maps id to incoming-offer window. The progress window (`ui/progress.rs`) has Pause/Resume, Minimize to background and Cancel; a lost connection shows a question after 3 s unless `Config.connection_lost` decides, and phase changes may return a notification (`PhaseNotice`) because label changes are not announced by screen readers. It shows the speed and the time remaining only in phases that move data and while some is still to come (`Progress::rate`), from `progress::Speed`, which the tray tooltip shares (`app::Transfer::rate`). A transfer whose data moved in its phase and then stopped for 5 s shows a speed of zero (`Speed::stalled`, `STALLED_AFTER`, checked by a 1 s timer that also refreshes the tray, `app::transfer_stalled`), since a peer that vanished is noticed only after the 30 s idle timeout; not before data moved (a restarted sender re-hashes before it sends), nor in this side's own work (packing, checking, unpacking). The connection line follows `Event::Path`, which is `None` once a transfer has no connection (both sides' `emit_waiting` send it before the waiting phase).

### Networking (`src/net/`)

- `protocol.rs`: ALPN `dodavo/3`. Every connection carries one bidirectional stream. A transfer is identified by a random 16-byte token in the `Offer` and may span several connections: `Offer` → `Accept|Decline` → `Data{len}` frames of raw bytes (≤ 256 KiB) → `Done{blake3 hash}` → `Verified{unpacking}` (the data matched) → `Result` (once the item is saved there, a folder unpacked); on a later connection the sender sends `Continue{token}` and the receiver answers `ContinueFrom{have}` (or `Gone`). `Paused`/`Resumed` may be sent by either side between frames, and `PartInUse{in_use}` by the receiver while another program keeps its part out; the receiver can ask `Query{token}` → `Alive|Gone`. Control messages are postcard-encoded with a u32 LE length prefix, capped at 64 KiB. The `Offer` also carries the size of a folder's largest file, so that the Incoming window and automatic acceptance refuse what a FAT32 destination cannot hold (files of 4 GiB or more: `incoming::check_space`, `Space::fits`, `archive::file_system`). There is no public release yet, so `Msg`/`Offer` may still change freely; once Dodavo is released, a change to them must bump the ALPN, because it breaks existing installs.
- `session.rs`: `TransferRecord` (JSON in `<data_dir>\transfers\<token>.json`, written once a transfer is accepted and deleted when it ends) lets a transfer continue after a lost connection or a restart; `net::start` restores the records at startup (`Event::Restored`). A tombstone `<token>.gone` is left when a side ends a transfer, with how it ended (`protocol::Ended`: completed, cancelled or failed), so `Continue`/`Query` get `Gone{ended}` and the other side reports a cancel only for a cancel (a completed one is never turned into another end; without a tombstone the answer is failed, `net::gone`). Both are forgotten after 30 days, as counted at two starts in a row (`session::Clock`: a clock that is wrong at one start ends nothing; each start notes its time in `transfers\last-start`), except the record of a receive that has all of its item (`done_hash`), which finishes without the sender however late, and a record that has `ended`, which the next starts keep until its files are deleted, but at most for 30 days after its end (`TransferRecord::ended_at`, set by `end_now`; a record of an earlier version counts from its file's modification time): then the start deletes what it can of the files once more, in the background, and forgets the record however that went (`TransferRecord::give_up`). A transfer in which nothing happened for 30 days expires: `load_all` ends it with its files (`discard`, quick: a part or a temporary archive) before anything goes on, and the start reports it as failed (`Event::Restored` with `goes_on: false`, then `Finished`, as for one whose part is missing; `error_expired_receiver_may_have` for a send whose receiver may have the item). `load_all` returns a `session::Found`: the records that go on, and those that are over with their `session::Fate` (`Ended`, `GivenUp`, `Expired`), which `net::restore_records` follows; `Verdict::part_under_its_name` tells which records claim their part's name for `follow_moved_part`. A record is read only from the file named after its token (a copy is set aside as `.json.bad`), and one that stays because some of its files could not be deleted names only what is left (`discard`, `ReceiveFiles.part_gone`), since a freed name may soon be another transfer's, and on FAT only the name tells. A record whose tombstone says `completed` (its deletion failed then) is only completed at the next start (`load_all` → `TransferRecord::complete`), never continued or discarded, because its item is in place. `TransferRecord::discard` marks the record `ended` before it deletes anything and removes it last, so a crash or a file that cannot be deleted yet leaves it for the next start, which only finishes the deletion. Files a record names carry their identity (`session::Owned`: path plus `archive::FileId`, volume serial and the 128-bit file ID, or the 64-bit file index on Windows 7; the part file's is `Side::Receive.part_id`), and a later start cuts, deletes, completes or reuses one only while it is still the same item. FAT and exFAT have no stable IDs: there a `FileId` holds the item's creation time instead (`FileId::same_item`, `archive::same_creation`: equal to the 10 ms that the file system keeps, or whole quarter hours apart up to 26 hours, because FAT keeps local time), so a file or folder made under the name later is not the transfer's. Windows gives a new item, or one renamed to a name, the creation time of an item of that name deleted moments before ("tunnelling"), so a new part and a new folder to unpack into get the time of their creation (`archive::created_now`, `Owned::made_at`; a part fails on FAT when its time cannot be set), a renamed part gets its own back (`archive::keep_creation_time`), and the sender's creation date waits until the record is gone where it would change the item's identity (`ItemTimes::split`, `receive::finish_file`). Identities without a creation time (records of earlier versions) are the same for every item of a volume, and then the name decides (`FileId::tells_apart`; whether a part was renamed is told by the sizes there, see `TransferRecord::follow_moved_part`; tests simulate FAT with `archive::PRETEND_FAT` and earlier versions with `FileId::without_creation_time`). Where the part's identity is its creation time, what has its name is not the part while it is shorter than `synced` (`TransferRecord::part_shorter`), since a file made under the name within the tunnelling window gets that time; elsewhere a part that lost its end goes on from what is there (`TransferRecord::have`). The receiver opens its part by name for each connection and checks it on the handle it writes to (`TransferRecord::open_part`, `receive::open_own_part`), which shares it only for reading, so that no other program can delete, rename or write to it during the connection (while another program keeps it out, the connection waits for it as long as the connection lasts, with nothing lost and, after a moment, the status saying so on both sides, `receive::open_for_connection`, `Phase::PartInUse`, `Msg::PartInUse`); a cancel meanwhile deletes it through a second handle that the session keeps (`Session::keep_part`, `archive::delete_on_close`), since a write may still be under way, after the record is saved as ended. The last step opens it once, so that others can only read it (`receive::Transfer::open_part`, without delete access where it is not renamed; it waits as a connection does while another program keeps the part out, `Phase::PartInUse { finishing: true }`, which a cancel ends), and renames it (`archive::rename_open`, `move_open_to_unique_noted`) and unpacks it through that handle, so that what it acts on is what was checked. The end of a running transfer tries again for a moment to delete a file that is held, being deleted or mapped into memory (`session::remove_file`, `patient`, `archive::delete_held`); a start does not wait. Folders that could not be deleted yet are kept in `ReceiveFiles.leftovers` until the transfer ends (`ReceiveFiles`, flattened into `Side::Receive`, holds what the last step of a receive changes: the part, `unpacking`, `moving`, `leftovers`). `Session` (per running transfer) routes a new connection to its task and holds the current connection, and its state lock guards the record together with the stage (`Running`, `Finishing`, `HandedOver`, `Ended`) that decides what a cancel does (`Session::cancel` → `Cancel::Ended|LeftToStep|TooLate`; once `Session::end` has run, a cancel is too late and the outcome stays the task's). No file work holds that lock: records are written through `Session::save_with`, in the order of the changes, under a separate `writing` lock, which an `Ending` also takes before it deletes the record. Saving a record syncs it to disk and ending a transfer may delete a large folder, so async code does that work through `session::off_runtime` (`Session::update`; `Session::end` and `cancel` only take the record and return an `Ending`, whose `forget` writes the tombstone and deletes the files); `Control` carries the cancel token and the pause flag (`watch`). Integrity stays one blake3 over the whole stream: the sender keeps hash snapshots every 64 MiB (`Snapshots`) and re-hashes the rest of the prefix with `hash_range` (its record notes how much has gone out every 64 MiB, `Side::Send::sent`, only so that a restored send shows how far it got until the receiver says, `TransferRecord::have`; `Sender::note_sent` writes it without holding up the data, and a panic in that write fails the send at the next note or connection, `SentNotes`, and each connection sets it back to what the receiver has); the receiver re-hashes its `.part` after a restart (`Phase::Verifying`). Neither that re-hash nor the cut back to `synced` at a restart fails while another program keeps the part out (a scanner or backup program after a crash): the re-hash waits as a connection does (`Receiver::rehash`), and the cut is left to the next connection, which waits for it (`Receiver::cut`, `cut_part`).
- `send.rs` / `receive.rs`: one task per transfer. The sender dials (with backoff) whenever the connection is lost; the receiver waits for `Continue` and queries the sender every 30 s. The receiver parks a `oneshot` in `Shared.pending` until the UI answers with `Command::Respond`. The sender's loop `select!`s between writing a frame (`SendStream::write` is cancel safe) and the receiver's messages; the receiver reads sequentially and lets a separate task own the `SendStream` (both give the receiver's status, under one lock: `receive::Status`). Close codes: `CLOSE_CANCELLED` (peer reports `CancelledByPeer`), `CLOSE_FAILED` (peer reports a failure), `CLOSE_SUSPENDED` (exiting or replacing the connection: peer treats it as lost and waits). Anything else, including timeouts, is a lost connection (`session::Lost`), never a failure. The text of a failure goes through `net::failure_text` (Windows' own text without Rust's "(os error N)", ours where tokio's files keep only the kind of an error, a general one for a panic, and "The connection was lost" for iroh's connection errors that only say that it ended, also inside the `io::Error` of a read or a write, `ends_connection`), and that of a dial that failed through `net::connect_error_text` (ours for a timeout and for an address that cannot be found). A checksum mismatch is reported over the stream (`Result{ok:false}`) and the connection is left open until the sender has read it. From `Done` on, the sender's cancel waits for the receiver's verdict (`Session::defer_cancel`, kept across a restart through `TransferRecord::done_sent`; the same while the record is first saved), so that the two sides never disagree on whether the item arrived: it ends the transfer only if the receiver turns out not to have the item (`ContinueFrom` on a later connection, `Session::stop_deferring`). Such a cancel is noted in the record (`TransferRecord::cancelled`) and issued again at the next start (`cancel_pending`, and the progress window shows it as being cancelled), and a cancelled send dials even while paused, since the window offers no Resume then (a record that says both is put right in `session::load_all`). `net::cancelled` emits `Event::CancelWaits` as soon as such a cancel is known to wait, before it is saved (a restored one is told by its record in `Event::Restored` instead; a cancel that the record already carries is not saved again, `Cancel::LeftToStep.to_save`): the progress window then still reports a pause by the peer and a lost connection (as it does for a send whose cancel came too late), because those hold up the cancel, and gives a balloon it withheld from a phase that arrived before `CancelWaits` (`Progress.balloon_withheld`); a cancel that ends its transfer in a moment gets no such balloons. A `ContinueFrom` while the cancel waited clears `done_sent` and needs the data again (it is checked then, not before: a restored send that the receiver may have goes on without its data, `receiver_may_have_item`). Once the data matched, the receiver sends `Verified` and the item is the receiver's: the sender waits for `Result` (`Phase::PeerUnpacking` while a folder is unpacked, with a notification), its cancel comes too late (`Session::hand_over`, kept across a restart through the sender's `done_hash`; `Event::HandedOver` makes the progress window drop Cancel and stop offering it when it is closed, with a status line that says why and, when the user had cancelled or the focus was on Cancel, a notification a moment later unless the transfer ends first (the receiver renames a file at once); `Phase::PeerUnpacking` is emitted before it), and a sender that dials again meanwhile is turned away until the tombstone answers `Gone{completed}`. Shutdown waits a moment only for cancels that end their transfer (`Control::cancelling`; a send's cancel that waits for the verdict counts until it is in the record). `net::cancelled` is what both directions race against their transfer for the user's cancel. `Command::Shutdown` suspends transfers instead of cancelling them; the UI sends `Cancel` first when the user chooses to.
- Received files are written as `<name>.part` and renamed at the end. What is kept of a received folder (`config::ReceivedFolder`, chosen at accept time and sent with `Command::Respond` as `net::Accept`, stored in `Side::Receive.folder`): `Extract` receives a temp zip (`recv-<token>.zip`, a `session::temporary_part`) and extracts it into a new folder; `KeepZip` and `Both` receive `<name>.zip.part` in the destination; `KeepZip` renames it to `<name>.zip` at the end, `Both` before unpacking, together with the new folder so that both get the same number (`new_pair`), and then unpacks from the zip at its final name. Sent folders are zipped to `send-<token>.zip` (`session::temp_archive`). Names in the destination are taken without replacing anything: parts are created exclusively, renames use `archive::move_to_unique` (no `MOVEFILE_REPLACE_EXISTING`, retried while a scanner holds the file), and the folder to unpack into is always created new (`archive::unzip` follows links in it) and noted in `ReceiveFiles.unpacking` before anything is written to it; after a restart that folder is deleted first and the archive is unpacked again into a new one, which gets the same name if the old one could be deleted (otherwise it becomes a leftover). Before each rename of the part, its target is noted in `ReceiveFiles.moving` (and the note is cleared when the rename fails), so after a crash right after the rename `restore` follows the part (`TransferRecord::follow_moved_part`, only when the part is no longer under its old name, also for a record that had ended, before its files are deleted) and a file or kept zip that was already in place completes (`placed_item`; the session is handed over first, so a cancel that is already waiting comes too late). The last step runs on a blocking thread inside `Session::finishing`: a cancel meanwhile is left to it (`Session::cancel` marks the record `ended` and returns `Cancel::LeftToStep`, the next note of the step's files fails with `archive::Cancelled`, `unzip` stops, `finish_folder`'s `Cleanup` guard removes the folder, and the transfer then ends as Cancelled), so the record names the folder until it is gone. The item is put in place by `Session::place`, which ends the transfer as completed right away, before the grace wait for the sender: from then on a cancel is too late (`Cancel::TooLate`, and the outcome stays Completed; a failure after it is still reported as one, because only an `archive::Cancelled` error makes the outcome Cancelled; a panic after it is not, `net::guarded`), and a completed receive only deletes a temporary part (`TransferRecord::complete`), because the part's old name may already belong to another transfer. Until then partial output is kept while a transfer can continue and removed when it fails or is cancelled (all or nothing, also for `Both`, whose zip goes with the part). A receive makes its part and record on a thread of its own, which a cancel does not wait for (`receive::First`, taken once the part exists and before the record is made, decides whether the transfer or the cancel has them; if the cancel came first, the thread deletes the part and makes no record), and registers its session before anything else is raced against a cancel, so that `cancelled()` always finds what to delete. The notes of the last step (`Session::save_receive_files`) stop it only with `archive::Cancelled`; a record that cannot be saved then does not fail an item that arrived intact. When the user closes a progress window with Cancel, it is only hidden until the transfer ends, so that a cancel that came too late is still reported (`Progress.closing`, notification `notify_too_late_title`).
- Dates: the `Offer` carries the item's own modified/created times (FILETIME `u64`), and `archive::zip_folder` stores each entry's times as the MS-DOS date (local time) plus the NTFS extra field 0x000A, which `archive::unzip` restores (folders deepest-first, after their contents). Of the attributes, only "hidden" travels (MS-DOS attributes in the zip, `archive::is_hidden`, set after the times by `archive::hide`): a read-only file would keep a partly unpacked folder from being deleted on FAT and before Windows 10 (std's `remove_dir_all` ignores read-only only with POSIX deletion), and a read-only or system folder makes File Explorer follow the peer's `desktop.ini`. Every kept received file gets the Mark of the Web (`archive::mark_of_the_web`, the `Zone.Identifier` stream, ZoneId=3), written before the times are set, because writing the stream changes the modified date.
- `bind()` in `net/mod.rs` configures the endpoint (n0 preset relays + mDNS). This is where a self-hosted relay would be configured.

### Updates (`src/update/`, `src/ui/update.rs`)

`update::mod` fetches the signed manifest from the fixed GitHub URL (`MANIFEST_URL`), verifies the Ed25519 signature (`keys.rs`, `statement.rs`) before trusting anything in it, compares versions (`version.rs`, hand-written semver) and downloads the installer while hashing it. Each check or download runs on its own thread with a `current_thread` tokio runtime and reports `update::Event`s through `app::update_sink`; `App.update_job` identifies the current job, so cancelling is forgetting the job, and events of old jobs are dropped. `ui::update` owns the "Update Available" window (modeless, like the incoming window), the scheduler (`tick()`: 15 s after start, then hourly it checks whether 24 h have passed; `Config.check_updates`, `update_last_check`, `update_remind_after`) and the manual check. Installing: Setup is started with the plain `open` verb (never elevated by Dodavo) and `/VERYSILENT … /CURRENTUSER|/ALLUSERS /DODAVOUPDATE=<pid> /DODAVOARGS="--updated …"` (`update::install_mode` compares the exe folder with the HKCU/HKLM uninstall registrations). For all users Setup elevates itself (Windows asks). Its `InitializeSetup`, which runs in the elevated process before Inno's own AppMutex check, posts `Dodavo_ExitForUpdate` to every `Dodavo_Main` window and waits for the pid and the `Local\DodavoRunning` mutex; the main window's handler closes the instance mutexes (`main::release_instance_mutexes`) and exits (the installing instance as chosen in the window, `App.update_cancel_transfers`; other profiles with transfers suspended). Until then Dodavo keeps running and only watches whether Setup ended early (declined elevation → exit code 1 → error in the window). `PrepareToInstall` waits once more, and the second `[Run]` entry (`runasoriginaluser`) starts Dodavo again unelevated. The message name, the class name and the parameters are a contract between the program and every future installer. `manifest.rs`, `statement.rs`, `version.rs` and `keys.rs` are `#[path]`-included by the release tool, so they must not use `crate::` paths. Bumping `format` in the manifest makes old programs ignore it.

### Other modules

- `archive.rs`: folder zipping/unzipping, which rejects unsafe paths with its own check of the entry names (`entry_path`, `is_plain_name`, `is_device_name`: the zip crate's `enclosed_name` panics on ordinary names such as "Kuća.jpg" in zip 9.1 and 9.2). It also provides `sanitize_file_name`, `file_id`, `name_taken` (also true for a deleted file that is still open somewhere, which keeps its name and makes creating it fail with access denied) and the functions that take a free name in one step without ever replacing anything (`create_unique_file`, `create_unique_dir`, `move_to_unique`, `rename_new`); there is deliberately no "find a free name" function to use later. Any name coming from a peer must pass through these.
- `i18n/`: translations. `mod.rs` lists every key in the `strings!` macro; each language (`en.rs`, `hr.rs`, `sr_latn.rs`, `sl.rs`) is one `Strings` const, so a missing translation fails to compile. Use `tr!(key)` / `tr!(key, name = value)` for `{name}` placeholders and `trn!(key, n, …)` for number-dependent text (CLDR plural categories; Slovenian has a dual). Build sentences as whole strings per variant (no "file"/"folder" word splicing), and keep peer names out of positions that need grammatical case (use "– primatelj: {name}" or parentheses). Tests check placeholders and that access keys are unique per window/menu; add new controls with access keys to the groups in `access_keys_are_unique`. The language comes from `DODAVO_LANG`, then the `language` setting, then the Windows display language (English fallback), and is fixed for the process lifetime.

The license texts stay in English. Help → Donate opens `ui::DONATE_URL` in the browser (`about::open_link`). Setup deliberately has no Welcome and no license page (see the comment in `Dodavo.iss`) and installs both files next to the program.
- Help: `res/help/<lang code>.html` (one page per language, plus the shared `help.css`) is built in by `ui/help.rs`, written to `%TEMP%\Dodavo\help` and opened in the default browser in the current UI language (Help → View Help, or F1 in any window via `main_window::translate`). Pages follow WCAG 2.2: one `<h1>`, no skipped heading levels, landmarks, a skip link, `<kbd>` keys, and keyboard/screen reader instructions for every task. When you change a feature or a UI string, update all four pages. Tests check that the pages have identical ids and heading structure, that links resolve, and that they quote the program's current texts.
- `config.rs`: JSON settings and contacts in `%APPDATA%\Dodavo[\profile]`, including migration from the old `QuickAndEasyFileTransfer` folder. A damaged `config.json` is moved aside (`config.json.bad`) and reported at startup rather than silently replaced. `identity.rs` stores the secret key there and refuses to overwrite an existing but unreadable or damaged `secret.key`.
- `ui/window.rs`: a small framework over raw Win32. Each window owns a `Handler` trait object. Control rects are in 96-DPI units and scaled automatically. It handles fonts, DPI changes, theming, and modal loops (`run_modal`). While a handler is borrowed (it opened a modal window, message box or task dialog), messages to its window skip it; messages that must not be lost and need no handler state go through `CreateOptions::urgent` (the main window's `urgent_message`: `Dodavo_ExitForUpdate`, end session, `TaskbarCreated`). Framework windows have no owner, so destroying the main window does not close a `run_modal` window: `main_window::exit` posts `WM_QUIT` at once, which ends every open dialog loop (`run_modal` then closes its window). `Window::text_height` measures wrapped label text, which follows the Windows text size (DPI scaling alone does not). Use `with_handler::<T>` to reach a window's handler from outside. New dialogs should follow the existing ones (`settings.rs`, `recipient.rs`, `incoming.rs`). The per-monitor DPI functions (Windows 10 1607) are looked up at run time in `dpi_api()` with system-DPI fallbacks.
- `ui/main_window.rs::translate` does accelerators and Tab navigation (`IsDialogMessageW`) for the main loop.
- `ui/theme.rs`: light/dark handling for the title bar, menus and controls. `ui/tray.rs`: the notification-area icon and balloons. `ui/shell.rs`: shell integration (Start with Windows, etc.).
- Single instance per profile through a named mutex. A second launch posts `show_message_id()` to the existing main window. Every instance also holds `Local\DodavoRunning`, which is the installer's `AppMutex`; keep both names in step.
- `installer/`: `Dodavo.iss` (per-user by default, fixed `AppId`, never change it), `build.ps1`, and `languages/` with adapted Croatian and Serbian (Latin) Inno Setup translations (formal address, Windows terms). Setup must offer the same languages as `src/i18n`. When you add a language, add its `.isl` (official or vendored and reviewed) to `[Languages]`. The help's "Installing and uninstalling" section quotes Setup's texts.

Win32 calls mostly use `windows-sys`. The `windows` crate is used only for COM shell APIs. Strings go through `ui::wide` / `ui::from_wide_ptr`.

## Guidelines

- **Windows 7 SP1 is the oldest supported Windows.** Never import a Win32 function statically that is newer than Windows 7 SP1 (for example the `*ForDpi` functions, `SetThreadDescription`, anything in `combase.dll`, `shcore.dll` or an `l1-2-*` API set): the loader then refuses to start the program on older Windows. Resolve it with `GetModuleHandleW`/`GetProcAddress` and fall back (pattern: `dpi_api()` in `ui/window.rs`, `api()` in `ui/theme.rs`), and avoid `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_SYSTEM32` for anything that must work on an unpatched Windows 7. The `windows`/`windows-sys` crates bind some functions to Windows 8 DLLs (`CoTaskMemFree` → `combase.dll`); declare those yourself against the old DLL, as `ui/shell.rs` does. Stable Rust itself only supports Windows 10+, so the Windows 7 builds use the Tier 3 win7 targets (see Commands). After changing Win32 calls or dependencies, run `installer\check-imports.ps1` on the release exe. Structs like `NOTIFYICONDATAW` are packed on 32-bit: don't take references to their fields.
- **Avoid `unsafe`.** Use it only when there is no safe alternative, which in practice means direct Win32/FFI calls. Keep each `unsafe` block as small as possible, and prefer safe wrappers (for example, the helpers in `ui/mod.rs` and `ui/window.rs`) or safe crate APIs over new raw calls.
- **Accessibility is a high priority.** Every feature must work fully with screen readers (NVDA, JAWS, Narrator) and with the keyboard alone:
  - Every control needs an accessible name. Put a visible label right before it in creation order, or set the name explicitly.
  - Tab order must be logical, Enter and Escape must work, and menu items need access keys and shortcuts.
  - Status changes such as progress, completion and errors must be perceivable without seeing the screen.
  - Don't rely on color alone. Owner-drawn or custom-themed controls must keep working with assistive technology.
- **Localization.** Whenever you add or change a user-facing string, update the translations for every supported language in the same change. Never leave a language behind or fall back to English. When adding a new language, or translating into any language, check terminology, grammar and style against trusted sources for that language. Examples are official language institutes and dictionaries, and the Microsoft Terminology/Language Portal for Windows UI terms. Use Windows' own established terms for that language (for example "Downloads", "notification area", "Settings") so the app is consistent with the system.
