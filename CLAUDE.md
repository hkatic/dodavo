# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dodavo is a Rust app for sending files and folders directly between computers and phones over [iroh](https://iroh.computer), with a native interface on each system: classic Win32 on Windows (`src/main.rs`, `src/app.rs`, `src/ui/`), AppKit in Swift on macOS (`macos/`, over `crates/dodavo-ffi`) and Jetpack Compose in Kotlin on Android (`android/`, over `crates/dodavo-android` and `crates/dodavo-ffi`), all on the library `dodavo_core` (`src/lib.rs`). Most of what follows was written for Windows; see [The Mac version](#the-mac-version) and [The Android version](#the-android-version) for what differs. Peers are identified by a **Contact ID** (the iroh public key), not an IP address; it stays the same until the user changes it (see Change My Contact ID under Other modules). See README.md for the user-facing feature list.

## Commands

- Build: `cargo build --release` → `target\release\Dodavo.exe`. Needs the MSVC toolchain and Windows SDK (`rc.exe`); `build.rs` embeds `res/app.rc` and `res/app.ico` via `embed-resource`, with `res/app.manifest` as a template (`@VERSION@`) and the values of the version resource in a generated `app-info.h`, both written to `OUT_DIR`. `.cargo/config.toml` links the C runtime statically for every target. 32-bit: `cargo build --target i686-pc-windows-msvc`.
- Installer: `powershell -ExecutionPolicy Bypass -File installer\build.ps1` → `target\installer\Dodavo-<version>-setup.exe` + `.sha256`. Needs Inno Setup 6.6+ (32-bit edition). It builds four programs: x64 and x86 with stable Rust for Windows 10+, and x64 and x86 for Windows 7 SP1–8.1 with the Tier 3 `*-win7-windows-msvc` targets on a nightly pinned in `build.ps1` (`-Zbuild-std`, own `target\win7` dir). `-SkipWin7` builds a Windows 10-only installer. Setup picks the build by Windows version and install mode (`[Files]` in `Dodavo.iss`). Signs with signtool when `DODAVO_SIGN_THUMBPRINT` or `DODAVO_SIGN_PFX` is set (see README). Version, author (`authors`), website (`repository`) and copyright years (`[package.metadata.dodavo] copyright-years`) exist only in `Cargo.toml`: `build.rs` passes them to the program (`ui::COPYRIGHT_YEARS` via `DODAVO_COPYRIGHT_YEARS`), the manifest and the version resource (`CompanyName`, `LegalCopyright`, a custom `Website`), and `Dodavo.iss` reads publisher, copyright and URLs from that version resource. `README.md` repeats the copyright line; `about::tests` checks it. `build.ps1` stages the license files with CRLF line ends and a BOM for Setup (`LicenseFile`, `ThirdPartyLicensesFile`).
- Third-party licenses: `powershell -ExecutionPolicy Bypass -File installer\licenses.ps1` regenerates `res\third-party-licenses.txt` with cargo-about (`cargo install cargo-about --locked --features cli`; config `installer\about.toml`, template `installer\about.hbs`), plus a section for the Rust standard library from the `COPYRIGHT-library.html` of the active toolchain and the win7 nightly (its crates: std's closure in rust-src's `library\Cargo.lock` that the toolchain ships as `.rlib` for the host; installs rust-src). It writes the file only when the text changes (cargo rebuilds on its mtime). `build.ps1` runs it first. Run it after adding or updating dependencies or toolchains and commit the file with `Cargo.lock`; a new license must be GPL-3.0-compatible before it goes into `accepted`.
- Publish: `powershell -ExecutionPolicy Bypass -File installer\publish.ps1 [-Publish]` writes and verifies `target\installer\update.json` (the signed update manifest) from the built installer, `release-notes\<version>\<lang>.txt` and the secret key in `DODAVO_UPDATE_KEY_FILE` or `-KeyFile`, and with `-Publish` creates the GitHub release `v<version>` through `gh`, as a draft that goes public after a confirmation. The release tool behind it: `cargo build --release --features release-tool --bin dodavo-release` (`keygen`, `manifest`, `verify`). The private release guide lives outside the repo (`C:\Users\hrvoj\Documents\Dodavo-release\RELEASING.md`). The repository is public (https://github.com/hkatic/dodavo, default branch `master`) and has the releases, from 1.0.0 (`v1.0.0`) on. Commits use the GitHub noreply address, so that no private address becomes public: `git config user.email 4093758+hkatic@users.noreply.github.com` in a new clone.
- CI: `.github/workflows/ci.yml`, on every push to `master` and `dev` and on pull requests. `windows` builds the 64-bit program, checks its imports and runs all tests. `windows-all-builds` runs `installer\build.ps1`, so all four programs with their import checks and an unsigned Setup, kept as an artifact of the run for 14 days, and then runs all tests on the 32-bit program. `macos` and `android` are described below. A release is still built and signed locally.
- Import check: `powershell -ExecutionPolicy Bypass -File installer\check-imports.ps1 <exe> [-Profile win7]` fails when an exe imports a DLL or function newer than its Windows baseline. `build.ps1` runs it on every build; run it after touching Win32 calls or dependencies.
- Test everything: `cargo test`
- Single test: `cargo test <name>`, e.g. `cargo test end_to_end` or `cargo test archive::`
- `net::tests::end_to_end`, `resume_after_disconnect`, `resume_after_restart`, `finish_alone_after_restart_during_unpacking`, `a_cancel_waits_for_the_verdict_across_a_restart`, `a_send_needs_its_data_again_when_the_receiver_lacks_it`, `a_blocked_sender_is_declined_unseen`, `a_shared_copy_goes_with_its_transfer`, `a_document_goes_as_the_app_describes_it`, `a_chat_goes_both_ways`, `a_chat_is_refused_unseen`, `an_answer_is_taken_from_someone_the_user_wrote_to`, `a_side_without_chat_says_so`, `a_chat_goes_while_transfers_run_both_ways`, `a_send_to_another_version_says_so` and `a_part_changed_between_connections_fails_the_transfer` start two real iroh endpoints in one process and need internet access (address lookup / relays). Run them with `--test-threads=1`; each can take a minute or two. One that starts two endpoints calls `reach` before it sends what it is about: where the local network is closed to the test (GitHub's Mac runner), a new endpoint is found only a moment after it is online, and a send that does not find its receiver ends as unreachable, with nothing to try it again.
- Built-in sounds: `cargo run --example gen_sounds` writes `res/sounds/*.wav` from `src/sound_synth.rs` (commit them; `sound::tests` checks that they are current). The library includes the files, so when one is missing nothing builds: `rustc --edition 2024 examples/gen_sounds.rs` makes the generator alone.
- Run two instances side by side: `Dodavo.exe --profile alice` and `Dodavo.exe --profile bob` (separate identity and settings). `--minimized` starts in the tray. `--send <paths>` offers items for sending, as File Explorer's menus do; everything after it is a path.
- Update testing: `DODAVO_UPDATE_URL` overrides the manifest URL (a local `python -m http.server` works) and `DODAVO_UPDATE_KEY` the trusted public keys (hex). `--updated` is what Setup starts the program with after an update.
- Force theme for testing: set `DODAVO_THEME=dark` or `DODAVO_THEME=light`. Force language: `DODAVO_LANG=en|hr|sr-Latn|sl`. `DODAVO_LEGACY_DPI=1` uses the Windows 7/8 DPI code path (system DPI only) on a current Windows. `DODAVO_RELAY_ONLY=1` binds the endpoint without IP transports (`net::RELAY_ONLY`), so that everything goes through the relays; `a_chat_goes_through_a_busy_relay` does that in a test that pushes data through the public relays and is `#[ignore]`d (run it by hand with `--ignored --test-threads=1`).
- Debug builds keep a console window; release builds use the `windows` subsystem. A panic hook shows a message box: after a panic on the UI thread or in the network thread's own loop the program ends; one on another thread shows it from a thread of its own (one at a time), and the program goes on: a transfer whose task panicked fails with "An unexpected error occurred", its leftovers are deleted and the peer is told that it failed, unless it had ended already, which then stands: one that had completed (a received item in place) is reported as completed (`net::guarded`, `Session::ended`; the last step of a receive passes a panic on to it, `receive::Receiver::finalize`).

## The Mac version

Apple Silicon, from macOS 11 (Intel Macs later). Nothing else about the project changes: `dodavo/3` is the same protocol, and a Mac exchanges transfers with released Windows copies.

Commands (Rust needs `MACOSX_DEPLOYMENT_TARGET=11.0`, which `build.sh` sets):

- Build: `macos/build.sh [--debug]` → `target/macos/Dodavo.app`, with the Rust library, `swiftc` and the bundle. It calls `swiftc` itself: Xcode's build system refuses macOS 11 by now, and SwiftPM quietly raises it to 12, while the compiler and the linker still take it. It signs with `$DODAVO_SIGN_IDENTITY`, or ad hoc without one.
- Floor check: `macos/check-floor.sh <program>`, the counterpart of `check-imports.ps1`; `build.sh` runs it. The compiler rejects Swift APIs newer than the target, so use `if #available` for them; this checks what it cannot.
- Tests: `cargo test --workspace`. `archive::macos_volumes` runs a receive on real APFS, HFS+, FAT32 and exFAT disk images. Windows cannot be built here, but it can be type-checked (see `macos/check-windows.sh`), and GitHub Actions builds and tests it on every push: run both after touching shared code.
- Test peer: `cargo run --example peer -- --profile peer --out <dir>` is a peer without a user interface that accepts every offer and takes commands on its input (`send <contact id> <path>`), for trying transfers with other copies.
- Two instances: `open -n target/macos/Dodavo.app --args --profile alice`.
- Final release: `macos/release.sh [--skip-tests] [--allow-changes]` is all of it in one command: it checks what it needs, runs the tests, builds, signs and notarizes, and checks the result as macOS checks a download. It refuses uncommitted changes, license texts that have changed, a version that was released already, and two `Cargo.toml` files with different versions. It publishes nothing.
- Disk image alone: `macos/make-dmg.sh [--no-notarize]` → `target/macos/Dodavo-<version>-macos.dmg`. Publish: `macos/publish.sh [--key <file>] [--publish]`. Licenses: `macos/licenses.sh` → `res/third-party-licenses-macos.txt`, after changing dependencies. Icon: `swift macos/Resources/make-icon.swift macos/Resources/Dodavo.icns`.
- Accessibility: `macos/tests/ax_audit.swift` fails on a control without a name (it needs the Accessibility permission and an unlocked screen), and `macos/tests/voiceover-checklist.md` is what to go through by hand. What VoiceOver really says can be read while it runs (`osascript -e 'tell application id "com.apple.VoiceOver" to return content of last phrase'`, with AppleScript allowed in VoiceOver Utility), and it does not always follow the accessibility tree: check speech, not only names.

How it is built:

- `crates/dodavo-ffi` holds the state of the program (as `app.rs` does on Windows) and speaks JSON to Swift through `dodavo_start`, `dodavo_poll`, `dodavo_call` and `dodavo_free` (`dodavo_sound` gives the bytes of a built-in sound). Its callback only wakes the main thread, which then takes messages from a queue, as with `WM_APP_NET`; rows of a transfer replace one that was not taken yet. Network events go through a thread of its own, since the first use of Downloads may wait for the user to allow it. Swift draws what it is told and passes on what the user does, and holds no state of a transfer.
- `src/view.rs` (`TransferView`) works out what a transfer shows and what can be done with it, by the rules of `ui/progress.rs`. Windows uses only its stateless parts (`Speed`, `describe`, `can_pause`, ...) so far, and keeps its own state; when one changes, change both (see `TODO.md`).
- Texts: `src/i18n/mac/` is a table of its own for the Mac interface, with Apple's terms, and a missing translation fails to compile as it does elsewhere. Where the shared code says something differently on a Mac ("app", a volume's name), the key is in both tables and the code uses `os_tr!`. `macos/Sources/Dodavo/Keys.generated.swift` is made from it by `gen_keys` (a test checks it is current), so a wrong key fails to compile in Swift too. `gen_lproj` writes what macOS itself shows per language. `Settings…` and `System Settings` are `Preferences…` and `System Preferences` before macOS 13.
- Help: `res/help/macos/` has its own pages, with tests in `crates/dodavo-ffi/src/help.rs`; they name no Windows things. Update all four when a feature or a text changes.
- Swift: language mode 5 and no `async`, as Swift's concurrency would need a library of its own in the app on macOS 11. Sheets rather than `runModal`, except for quitting and fatal errors. Only standard controls, each with a label, with `announce` for what changes without moving the focus; automatic events never take the focus.
- VoiceOver, as tried on macOS 27: it does not say a linked title (`setAccessibilityTitleUIElement`), so name a control with `name(_:by:)` (`Speech.swift`). A button says its title rather than its description, so use `setAccessibilityTitle` to add to it. A text field or an image is left out through its `cell`, not the view. Custom actions on a table cell are listed twice, and VoiceOver offers a cell's buttons as actions by itself, so have none there. An announcement is not spoken from the background, and one made as a sheet closes is lost. One made while VoiceOver tells of a window that has just opened, or of where the focus has just gone, takes the place of that or is lost itself: make it a moment later and not urgent, so that it waits its turn (`MainWindowController.say` for 2 s after the window opens or becomes the key window, `SettingsWindowController.unblockSelected`, which first checks that the user is still at the list). A window made in code has no key view loop unless `autorecalculatesKeyViewLoop` is on, and Tab passes over the buttons in the rows of a table, so `TransfersTable` gives them keys.
- Notifications, as tried on macOS 27: a click on one also reaches `applicationShouldHandleReopen`, which must not bring the main window in front of where the click leads (`AppDelegate.perform`). A `.foreground` action brings Dodavo in front of the app that opens the item, so the actions have none; the Finder needs asking to come to the front then. VoiceOver reads a notification as it appears, so the end of a transfer is not announced as well (`Notifier.showsEndOfTransfer`).

Where POSIX does not do what the transfers rely on (`src/archive/macos.rs`, under `cfg` in `net/receive.rs`):

- There are no share modes, so nothing keeps other programs from writing to, renaming or deleting a part during a connection. So a Mac hashes the part again from the disk before `Verified` (`Receiver::pump`), through a handle checked against the part's identity, failing if it is longer than what arrived, and every 64 MiB notices a part that was moved or deleted (`Receiver::check_part`). The `Phase::PartInUse` wait stays for what does keep it out (`is_busy`: `EBUSY`, and `EPERM`/`EACCES`, which are what a denial in Privacy & Security looks like).
- Only `NotFound` means that an item is gone (`archive::cannot_tell`): otherwise a denial in Privacy & Security would make a start discard a transfer, and a later one delete its part.
- Identity (`FileId`): volume UUID and inode on APFS and HFS+; the creation time on FAT and exFAT, whose inodes are made up (no birth time on APFS: `ItemTimes::split` would change an item's identity); elsewhere (SMB) the name decides. There is no tunnelling, so `created_now` and `keep_creation_time` do nothing. FAT32 reads creation times in whole seconds here. On FAT and exFAT, macOS keeps attributes in a file beside each file (`._name`), also for ones it adds by itself.
- Renames that replace nothing are `renamex_np(RENAME_EXCL)`, with a placeholder where the volume cannot do it. `rename_open` goes by `F_GETPATH` and then checks what it renamed. `delete_on_close` cannot be done, and need not be: deleting by name always works.
- `sync_data` is `F_FULLFSYNC`, which some file systems refuse (`sync_part` falls back to `fsync`). Temporary archives are in `Application Support/Dodavo/tmp`, since macOS empties `$TMPDIR` while a transfer may wait for much longer. The mark of the web is `com.apple.quarantine`, on folders too.

Exchanging folders with Windows: a released Windows receiver stops at the first zip entry whose name Windows cannot take (`is_plain_name`), after all the data has arrived, and a sender cannot tell what system the other side runs. So a Mac writes only such names (`archive::names`), unique once case does not count, leaves out what only means something to macOS, and keeps the original name and the links that stay inside the folder in a private extra field (`0x6464`) that Windows ignores. What a peer says there is checked before it decides where anything goes. Mode bits other than "executable" do not travel. Keep this working with a released Windows `unzip`.

Updates: `update-macos.json` next to `update.json` on each release, with a statement prefix of its own (`statement::Platform`), so that a manifest never verifies on the other system. Installed copies read the manifest of the latest published release, so every release has to carry both (see README). After the download, `Installer` (`UpdateWindow.swift`) mounts the image, checks the signature and the team, swaps the app with `RENAME_SWAP` and relaunches.

Releases: `macos/release.sh`, on the Mac that has the certificate "Developer ID Application: Hrvoje Katic (3GAM6Z3A2W)", with the notary profile `dodavo` in its keychain. A copy that has the mark of a download is translocated unless it runs from its disk image. `Relocation` removes that mark from the copy it makes in Applications, once its signature checks out, as macOS would otherwise ask the user a second time about what they just allowed, and ejects the disk image.

Commands (JDK 21: Android Studio's JBR; the Android SDK with NDK r30 `30.0.16248370`; `cargo-ndk`; `rustup target add aarch64-linux-android x86_64-linux-android`):

- Two copies: the app and `examples/peer` on a computer, or two devices.

How it is built:

- `crates/dodavo-android` is `libdodavo.so`: the natives `start`, `call`, `poll` and `next` of `com.hrvojekatic.dodavo.core.Native`, each catching a panic (`with_env`), over the Rust API of `dodavo-ffi` (`start`, `call`, `poll`, `wait`). `start` gives iroh the JVM and the app's context once (`platform::install_android_jni_context`, before the network starts) and registers the document opener. Never `panic = "abort"`.
- Kotlin: `DodavoApp` starts the core with the process; `NativeCore` has one thread waiting in `next(1000)`, so waking the UI never calls into Java; `CoreRepository` turns the messages into `StateFlow`s, and is the one source of truth; its status line begins with what the core's answer to the start says (`Started.status`, "Connecting to the network…"), before the screens show it. One `AppCompatActivity` (per-app languages), Navigation 3 with `NavigationSuiteScaffold` (a bar on phones, a rail on wider windows), a ViewModel per screen, manual injection through `AppContainer`, DataStore for what only the app keeps (Receive in the background, the first-start question).
- Running outside the screens (`service/`): `DodavoService` is a foreground service of type `dataSync` while data moves and `connectedDevice` with Receive in the background (off by default; `BootReceiver` starts it after a restart only then); on Android 15 and later `onTimeout` ends `dataSync` for the day. `KeepAlive` turns events into notifications while Dodavo is not in front (an offer with Review and Decline, cancelled once answered anywhere), holds a Wi-Fi multicast lock for mDNS, and tells the core of network changes (`network_changed` → `Endpoint::network_change`).
- Storage: the app gives the core its folders (`platform::set_dirs`): data in `filesDir/Dodavo`, temporary files in `noBackupFilesDir/tmp` (never the cache, which Android may empty while a transfer waits), received items in `Download/Dodavo`, written by path (on Android 8 to 10 with `WRITE_EXTERNAL_STORAGE`). Android's backup leaves out `secret.key`, `transfers` and `running.lock`: two phones with one Contact ID would collide. `FileProvider` gives other apps a received file for Open and Share.
- Sending (`src/source.rs`): a picked file is a document (`content://`) that the core reads through `Documents.open` in Kotlin, by JNI from its own threads (the class is looked up on an app thread at start); the app keeps a persisted permission for it while a send reads it, and lets it go on `Out::DocumentDone`. A picked folder is packed from Kotlin's listing of the tree (`archive::zip_listed`) and needs no lasting permission. What another app shares, and a file that only opens as a stream, is copied into `<temp>/staging/<uuid>/`, which its transfer owns (`Side::Send::staging`).
- Accessibility: changes that do not move the focus go through the status line, a polite live region (`announceForAccessibility` is deprecated); every control has a name; a card's text is read as one item, with its buttons apart. Material 3's `ExtendedFloatingActionButton` with `icon` and `text` keeps its text from accessibility services: give it icon and text as content.

Where Android is not like the Mac (`src/platform/linux.rs`, `src/archive/linux.rs`, shared with Linux, and `src/archive/unix.rs`, shared with the Mac):

- Android's filter of system calls ends an app that calls `statx` or `renameat2` before Android 11, and Bionic before 11 has neither: both go through `libc::syscall`, only on API 30 and later (`platform::api_level`). `renameat2(RENAME_NOREPLACE)` gives `EINVAL` on the shared storage of some versions: then the placeholder rename.
- Identity: the inode number and the birth time from `statx`. There is no birth time before Android 11, on f2fs without it, and on the shared storage (`FileId::weak`), and ext4 gives a deleted file's number to the next one at once: a new part or folder of a receive leaves the names that records hold alone (`session::held_names`), and `part_shorter` and `session::Head` apply as on FAT (`TransferRecord::another_file`). What is left is in ISSUES.md. `open_path` reads `/proc/self/fd`.
- The shared storage takes only names that FAT could (`takes_name` with `is_plain_name`). There is no mark of the web and no hidden attribute; free space counts the data volume (`disk_free`).
- Google Play's rules: no Donate (`DONATE_URL` and `update` do not exist on Android, which the compiler holds to) and no updater of its own; no `MANAGE_EXTERNAL_STORAGE`, `REQUEST_INSTALL_PACKAGES` or request for a battery exemption. Blocking a sender is required of apps where users send each other things.

## Architecture

Two threads that never share UI state:

1. **UI thread** (`main.rs` message loop): owns all windows and the `App` state in `app.rs`, stored in a `thread_local!`. Access it only through `app::with(|a| …)`; do not create windows or show message boxes inside that closure, because they run nested message loops and would re-borrow the `RefCell`.
2. **Network thread** (`net::start`): a tokio multi-thread runtime that owns the iroh `Endpoint`.

They communicate in two directions:
- UI → net: `net::Command` (`Send`, `Respond`, `Cancel`) over an unbounded mpsc channel (`app::net_send`).
- net → UI: `net::Event` is pushed by `app::event_sink` into a global `EVENTS` queue (as `app::Queued::Net`; the update thread pushes `update::Event` through `app::update_sink` as `Queued::Update`), which then posts `WM_APP_NET` to the main window. `app::process_events` drains the queue on the UI thread. If a target window is busy (for example, a modal message box is open), the handler returns the event, which waits in `app::Backlog` together with the later events of the same transfer (`app::lane_of`; the update's events are a lane of their own) and is retried after 250 ms by a timer, while the events of the other transfers go on. Keep that contract when adding events, and give a new event that can wait its lane. `Progress` events may be dropped; the others must not be. The end of a transfer brings its size along for a window that dropped them all (`progress::finish`).

Transfer ids come from `net::next_transfer_id()` and are used in both directions (restored transfers get fresh ids). `App.transfers` maps id to progress window, and `App.offers` maps id to incoming-offer window. The progress window (`ui/progress.rs`) has Chat, Pause/Resume, Minimize to background and Cancel, and the check box "Close this window when the transfer ends"; after 3 s a lost connection does what `Config.connection_lost` says (by default it waits, with a notification; it can ask or cancel instead), and phase changes may return a notification (`PhaseNotice`) because label changes are not announced by screen readers. It shows the speed and the time remaining only in phases that move data and while some is still to come (`Progress::rate`), from `progress::Speed`, which the tray tooltip shares (`app::Transfer::rate`). A transfer whose data moved in its phase and then stopped for 5 s shows a speed of zero (`Speed::stalled`, `STALLED_AFTER`, checked by a 1 s timer that also refreshes the tray, `app::transfer_stalled`), since a peer that vanished is noticed only after the 30 s idle timeout; not before data moved (a restarted sender re-hashes before it sends), nor in this side's own work (packing, checking, unpacking). The connection line follows `Event::Path`, which is `None` once a transfer has no connection (both sides' `emit_waiting` send it before the waiting phase).

### Networking (`src/net/`)

- `protocol.rs`: ALPN `dodavo/3`. Every connection carries one bidirectional stream. A transfer is identified by a random 16-byte token in the `Offer` and may span several connections: `Offer` → `Accept|Decline` → `Data{len}` frames of raw bytes (≤ 256 KiB) → `Done{blake3 hash}` → `Verified{unpacking}` (the data matched) → `Result` (once the item is saved there, a folder unpacked); on a later connection the sender sends `Continue{token}` and the receiver answers `ContinueFrom{have}` (or `Gone`). `Paused`/`Resumed` may be sent by either side between frames, and `PartInUse{in_use}` by the receiver while another program keeps its part out; the receiver can ask `Query{token}` → `Alive|Gone`. Control messages are postcard-encoded with a u32 LE length prefix, capped at 64 KiB. The `Offer` also carries the size of a folder's largest file, so that the Incoming window and automatic acceptance refuse what a FAT32 destination cannot hold (files of 4 GiB or more: `incoming::check_space`, `Space::fits`, `archive::file_system`). Dodavo has been released (1.0.0), so a change to `Msg`/`Offer` must bump the ALPN, because it breaks existing installs: postcard reads a struct as a fixed sequence of fields, so even a new `#[serde(default)]` field changes the wire format. Peers with different ALPNs cannot connect: the side that is dialed answers with TLS's "no application protocol" alert (`net::no_such_protocol`), and a new send ends with word of that (`send::Undialed::OtherVersion`, `error_other_version`), while a transfer that was under way only waits for the connection (see `ISSUES.md`).
- `session.rs`: `TransferRecord` (JSON in `<data_dir>\transfers\<token>.json`, written once a transfer is accepted and deleted when it ends) lets a transfer continue after a lost connection or a restart; `net::start` restores the records at startup (`Event::Restored`). Later versions must keep reading the records of released ones (`#[serde(default)]` on new fields): an update restarts the program in the middle of a transfer, and a record that cannot be read is set aside as `.json.bad`, which loses its transfer. A tombstone `<token>.gone` is left when a side ends a transfer, with how it ended (`protocol::Ended`: completed, cancelled or failed), so `Continue`/`Query` get `Gone{ended}` and the other side reports a cancel only for a cancel (a completed one is never turned into another end; without a tombstone the answer is failed, `net::gone`). Both are forgotten after 30 days, as counted at two starts in a row (`session::Clock`: a clock that is wrong at one start ends nothing; each start notes its time in `transfers\last-start`), except the record of a receive that has all of its item (`done_hash`), which finishes without the sender however late, and a record that has `ended`, which the next starts keep until its files are deleted, but at most for 30 days after its end (`TransferRecord::ended_at`, set by `end_now`; a record of an earlier version counts from its file's modification time): then the start deletes what it can of the files once more, in the background, and forgets the record however that went (`TransferRecord::give_up`). A transfer in which nothing happened for 30 days expires: `load_all` ends it with its files (`discard`, quick: a part or a temporary archive) before anything goes on, and the start reports it as failed (`Event::Restored` with `goes_on: false`, then `Finished`, as for one whose part is missing; `error_expired_receiver_may_have` for a send whose receiver may have the item). `load_all` returns a `session::Found`: the records that go on, and those that are over with their `session::Fate` (`Ended`, `GivenUp`, `Expired`), which `net::restore_records` follows; `Verdict::part_under_its_name` tells which records claim their part's name for `follow_moved_part`. A record is read only from the file named after its token (a copy is set aside as `.json.bad`), and one that stays because some of its files could not be deleted names only what is left (`discard`, `ReceiveFiles.part_gone`), since a freed name may soon be another transfer's, and on FAT only the name tells. A record whose tombstone says `completed` (its deletion failed then) is only completed at the next start (`load_all` → `TransferRecord::complete`), never continued or discarded, because its item is in place. `TransferRecord::discard` marks the record `ended` before it deletes anything and removes it last, so a crash or a file that cannot be deleted yet leaves it for the next start, which only finishes the deletion. Files a record names carry their identity (`session::Owned`: path plus `archive::FileId`, volume serial and the 128-bit file ID, or the 64-bit file index on Windows 7; the part file's is `Side::Receive.part_id`), and a later start cuts, deletes, completes or reuses one only while it is still the same item. FAT and exFAT have no stable IDs: there a `FileId` holds the item's creation time instead (`FileId::same_item`, `archive::same_creation`: equal to the 10 ms that the file system keeps, or whole quarter hours apart up to 26 hours, because FAT keeps local time), so a file or folder made under the name later is not the transfer's. Windows gives a new item, or one renamed to a name, the creation time of an item of that name deleted moments before ("tunnelling"), so a new part and a new folder to unpack into get the time of their creation (`archive::created_now`, `Owned::made_at`; a part fails on FAT when its time cannot be set), a renamed part gets its own back (`archive::keep_creation_time`), and the sender's creation date waits until the record is gone where it would change the item's identity (`ItemTimes::split`, `receive::finish_file`). Identities without a creation time (records of earlier versions) are the same for every item of a volume, and then the name decides (`FileId::tells_apart`; whether a part was renamed is told by the sizes there, see `TransferRecord::follow_moved_part`; tests simulate FAT with `archive::PRETEND_FAT` and earlier versions with `FileId::without_creation_time`). Where the part's identity is its creation time, what has its name is not the part while it is shorter than `synced` (`TransferRecord::part_shorter`) or begins with other data than the record notes of the part's first 64 KiB (`session::Head`, which `Receiver::save_synced` notes as they reach the disk; `TransferRecord::another_file`), since a file made under the name within the tunnelling window gets that time; elsewhere a part that lost its end goes on from what is there (`TransferRecord::have`). The receiver opens its part by name for each connection and checks it on the handle it writes to (`TransferRecord::open_part`, `receive::open_own_part`), which shares it only for reading, so that no other program can delete, rename or write to it during the connection (while another program keeps it out, the connection waits for it as long as the connection lasts, with nothing lost and, after a moment, the status saying so on both sides, `receive::open_for_connection`, `Phase::PartInUse`, `Msg::PartInUse`); a cancel meanwhile deletes it through a second handle that the session keeps (`Session::keep_part`, `archive::delete_on_close`), since a write may still be under way, after the record is saved as ended. The last step opens it once, so that others can only read it (`receive::Transfer::open_part`, without delete access where it is not renamed; it waits as a connection does while another program keeps the part out, `Phase::PartInUse { finishing: true }`, which a cancel ends), and renames it (`archive::rename_open`, `move_open_to_unique_noted`) and unpacks it through that handle, so that what it acts on is what was checked. The end of a running transfer tries again for a moment to delete a file that is held, being deleted or mapped into memory (`session::remove_file`, `patient`, `archive::delete_held`); a start does not wait. Folders that could not be deleted yet are kept in `ReceiveFiles.leftovers` until the transfer ends (`ReceiveFiles`, flattened into `Side::Receive`, holds what the last step of a receive changes: the part, `unpacking`, `moving`, `leftovers`). `Session` (per running transfer) routes a new connection to its task and holds the current connection, and its state lock guards the record together with the stage (`Running`, `Finishing`, `HandedOver`, `Ended`) that decides what a cancel does (`Session::cancel` → `Cancel::Ended|LeftToStep|TooLate`; once `Session::end` has run, a cancel is too late and the outcome stays the task's). No file work holds that lock: records are written through `Session::save_with`, in the order of the changes, under a separate `writing` lock, which an `Ending` also takes before it deletes the record. Saving a record syncs it to disk and ending a transfer may delete a large folder, so async code does that work through `session::off_runtime` (`Session::update`; `Session::end` and `cancel` only take the record and return an `Ending`, whose `forget` writes the tombstone and deletes the files); `Control` carries the cancel token and the pause flag (`watch`). Integrity stays one blake3 over the whole stream: the sender keeps hash snapshots every 64 MiB (`Snapshots`) and re-hashes the rest of the prefix with `hash_range` (its record notes how much has gone out every 64 MiB, `Side::Send::sent`, only so that a restored send shows how far it got until the receiver says, `TransferRecord::have`; `Sender::note_sent` writes it without holding up the data, and a panic in that write fails the send at the next note or connection, `SentNotes`, and each connection sets it back to what the receiver has); the receiver re-hashes its `.part` after a restart (`Phase::Verifying`). On Windows nothing keeps other programs from the part between two connections of one run, so a part that an earlier connection wrote to is hashed again from the disk before `Verified`, while the connection's handle still holds it (`carried` in `Receiver::pump`); a Mac does that for every part (see The Mac version). Neither that re-hash nor the cut back to `synced` at a restart fails while another program keeps the part out (a scanner or backup program after a crash): the re-hash waits as a connection does (`Receiver::rehash`), and the cut is left to the next connection, which waits for it (`Receiver::cut`, `cut_part`).
- `send.rs` / `receive.rs`: one task per transfer. The sender dials (with backoff) whenever the connection is lost; the receiver waits for `Continue` and queries the sender every 30 s. The receiver parks a `oneshot` in `Shared.pending` until the UI answers with `Command::Respond`. The sender's loop `select!`s between writing a frame (`SendStream::write` is cancel safe) and the receiver's messages; the receiver reads sequentially and lets a separate task own the `SendStream` (both give the receiver's status, under one lock: `receive::Status`). Close codes: `CLOSE_CANCELLED` (peer reports `CancelledByPeer`), `CLOSE_FAILED` (peer reports a failure), `CLOSE_SUSPENDED` (exiting or replacing the connection: peer treats it as lost and waits). Anything else, including timeouts, is a lost connection (`session::Lost`), never a failure. The text of a failure goes through `net::failure_text` (Windows' own text without Rust's "(os error N)", ours where tokio's files keep only the kind of an error, a general one for a panic, and "The connection was lost" for iroh's connection errors that only say that it ended, also inside the `io::Error` of a read or a write, `ends_connection`), and that of a dial that failed through `net::connect_error_text` (always ours: a timeout, an address that cannot be found, another version, a connection that ended, and otherwise only that no connection was made, since the library's own words are in English). A checksum mismatch is reported over the stream (`Result{ok:false}`) and the connection is left open until the sender has read it. From `Done` on, the sender's cancel waits for the receiver's verdict (`Session::defer_cancel`, kept across a restart through `TransferRecord::done_sent`; the same while the record is first saved), so that the two sides never disagree on whether the item arrived: it ends the transfer only if the receiver turns out not to have the item (`ContinueFrom` on a later connection, `Session::stop_deferring`). Such a cancel is noted in the record (`TransferRecord::cancelled`) and issued again at the next start (`cancel_pending`, and the progress window shows it as being cancelled), and a cancelled send dials even while paused, since the window offers no Resume then (a record that says both is put right in `session::load_all`). `net::cancelled` emits `Event::CancelWaits` as soon as such a cancel is known to wait, before it is saved (a restored one is told by its record in `Event::Restored` instead; a cancel that the record already carries is not saved again, `Cancel::LeftToStep.to_save`): the progress window then still reports a pause by the peer and a lost connection (as it does for a send whose cancel came too late), because those hold up the cancel, and gives a balloon it withheld from a phase that arrived before `CancelWaits` (`Progress.balloon_withheld`); a cancel that ends its transfer in a moment gets no such balloons. A `ContinueFrom` while the cancel waited clears `done_sent` and needs the data again (it is checked then, not before: a restored send that the receiver may have goes on without its data, `receiver_may_have_item`). Once the data matched, the receiver sends `Verified` and the item is the receiver's: the sender waits for `Result` (`Phase::PeerUnpacking` while a folder is unpacked, with a notification), its cancel comes too late (`Session::hand_over`, kept across a restart through the sender's `done_hash`; `Event::HandedOver` makes the progress window drop Cancel and stop offering it when it is closed, with a status line that says why and, when the user had cancelled or the focus was on Cancel, a notification a moment later unless the transfer ends first (the receiver renames a file at once); `Phase::PeerUnpacking` is emitted before it), and a sender that dials again meanwhile is turned away until the tombstone answers `Gone{completed}`. Shutdown waits a moment only for cancels that end their transfer (`Control::cancelling`; a send's cancel that waits for the verdict counts until it is in the record). `net::cancelled` is what both directions race against their transfer for the user's cancel. `Command::Shutdown` suspends transfers instead of cancelling them; the UI sends `Cancel` first when the user chooses to.
- Received files are written as `<name>.part` and renamed at the end. What is kept of a received folder (`config::ReceivedFolder`, chosen at accept time and sent with `Command::Respond` as `net::Accept`, stored in `Side::Receive.folder`): all three receive `<name>.zip.part` in the destination, so that the drive the user chose is the one that needs the room; `Extract` unpacks it into a new folder and deletes it when the transfer completes (a `session::temporary_part`, deleted only while it is still that file, and with its record kept for the next start while it cannot be deleted: `TransferRecord::complete`); only a zip that the destination cannot hold (4 GiB or more on FAT32) arrives in the temp folder as `recv-<token>.zip` (`session::part_in_temp`, which `space::check_space` goes by too), as every such zip did in 1.0.0 and 1.0.1, whose records go on as they are; `KeepZip` renames it to `<name>.zip` at the end, `Both` before unpacking, together with the new folder so that both get the same number (`new_pair`), and then unpacks from the zip at its final name. Sent folders are zipped to `send-<token>.zip` (`session::temp_archive`) in the temp folder, or beside the folder, hidden, when the temp folder's drive lacks the room and the folder is on another drive that has it (`send::pack_in`, `new_zip`); a send has no record before it is accepted, so a zip outside the temp folder is noted first in `transfers\<token>.packing` (`session::note_packing`), by which a start deletes one that a crash left (`cleanup_packing`). Names in the destination are taken without replacing anything: parts are created exclusively, renames use `archive::move_to_unique` (no `MOVEFILE_REPLACE_EXISTING`, retried while a scanner holds the file), and the folder to unpack into is always created new (`archive::unzip` follows links in it) and noted in `ReceiveFiles.unpacking` before anything is written to it; after a restart that folder is deleted first and the archive is unpacked again into a new one, which gets the same name if the old one could be deleted (otherwise it becomes a leftover). Before each rename of the part, its target is noted in `ReceiveFiles.moving` (and the note is cleared when the rename fails), so after a crash right after the rename `restore` follows the part (`TransferRecord::follow_moved_part`, only when the part is no longer under its old name, also for a record that had ended, before its files are deleted) and a file or kept zip that was already in place completes (`placed_item`; the session is handed over first, so a cancel that is already waiting comes too late). The last step runs on a blocking thread inside `Session::finishing`: a cancel meanwhile is left to it (`Session::cancel` marks the record `ended` and returns `Cancel::LeftToStep`, the next note of the step's files fails with `archive::Cancelled`, `unzip` stops, `finish_folder`'s `Cleanup` guard removes the folder, and the transfer then ends as Cancelled), so the record names the folder until it is gone. The item is put in place by `Session::place`, which ends the transfer as completed right away, before the grace wait for the sender: from then on a cancel is too late (`Cancel::TooLate`, and the outcome stays Completed; a failure after it is still reported as one, because only an `archive::Cancelled` error makes the outcome Cancelled; a panic after it is not, `net::guarded`), and a completed receive only deletes a temporary part (`TransferRecord::complete`), because the part's old name may already belong to another transfer. Until then partial output is kept while a transfer can continue and removed when it fails or is cancelled (all or nothing, also for `Both`, whose zip goes with the part). A receive makes its part and record on a thread of its own, which a cancel does not wait for (`receive::First`, taken once the part exists and before the record is made, decides whether the transfer or the cancel has them; if the cancel came first, the thread deletes the part and makes no record), and registers its session before anything else is raced against a cancel, so that `cancelled()` always finds what to delete. The notes of the last step (`Session::save_receive_files`) stop it only with `archive::Cancelled`; a record that cannot be saved then does not fail an item that arrived intact. When the user closes a progress window with Cancel, it is only hidden until the transfer ends, so that a cancel that came too late is still reported (`Progress.closing`, notification `notify_too_late_title`).
- Dates: the `Offer` carries the item's own modified/created times (FILETIME `u64`), and `archive::zip_folder` stores each entry's times as the MS-DOS date (local time) plus the NTFS extra field 0x000A, which `archive::unzip` restores (folders deepest-first, after their contents). Of the attributes, only "hidden" travels (MS-DOS attributes in the zip, `archive::is_hidden`, set after the times by `archive::hide`): a read-only file would keep a partly unpacked folder from being deleted on FAT and before Windows 10 (std's `remove_dir_all` ignores read-only only with POSIX deletion), and a read-only or system folder makes File Explorer follow the peer's `desktop.ini`. Every kept received file gets the Mark of the Web (`archive::mark_of_the_web`, the `Zone.Identifier` stream, ZoneId=3), written before the times are set, because writing the stream changes the modified date.
- `bind()` in `net/mod.rs` configures the endpoint (n0 preset relays + mDNS). This is where a self-hosted relay would be configured. `Event::Online` says whether the endpoint is connected to its home relay server (`watch_online`). A new endpoint is not, for a moment, which says nothing about the network: it is reported as offline only once it has had 5 s (`online_report`, `ONLINE_GRACE`), so the status says that Dodavo is connecting at a start, and stays as it was while Change My Contact ID puts a new endpoint in the place of the old one. While no endpoint can be bound, `Event::BindFailed` says why at each try (`net::bind_error_text`: the system's words for an I/O error, and otherwise only that the network could not be opened), and `Event::Connecting` once one is bound after that. Each of the three replaces what the user interface knows of the network: it keeps the problem beside the online state and shows one status from both (`App.net_problem` and `main_window::show_status` on Windows, `State.net_problem` and `status` in the ffi). `NetHandle::is_up` says whether an endpoint is bound and commands are taken, which is what Change My Contact ID asks first, and not whether a status has come.

### Chat (`src/net/chat.rs`, `src/chat.rs`, `src/ui/chat.rs`)

Text messages between two people, on Windows and on a Mac (Android: `TODO.md`). The transfers know nothing of it.

- Network: an ALPN of its own, `dodavo-chat/1` (`protocol::CHAT_ALPN`, `protocol::ChatMsg`, framed as `Msg` is), so `dodavo/3` is untouched and released copies exchange files as before. A change to `ChatMsg` needs a new chat ALPN, for the same reason as `Msg`. An endpoint takes chat connections only when its user interface shows chats: `net::start_with_chat` with a `ChatPolicy` (Windows, the ffi on a Mac, `examples/peer`), while one without (`net::start`, the ffi on Android) lists only `dodavo/3`, so that no message is confirmed to its sender and then shown to nobody. `serve` tells the two by `Connection::alpn`. Who dials a side without chat gets TLS's "no application protocol" alert, which `chat::no_such_protocol` turns into "Dodavo on the other side does not have chat" (`os_tr!`: each system has its own word for a chat).
- One connection per pair, with one bidirectional stream that both write on: `Hello{name}` → `Welcome{name}` | `Refused`, then `Text{id, text}` → `Received{id}` and `Typing{on}` either way. It is dialed when something has to go out and none is there (`chat::send`), and closed after 5 minutes without a word (iroh keeps connections alive by itself). What is sent to a person waits in one `Queue`, whichever connection takes it (`Turn`: the task that sends now, the connection that takes over, the messages waiting), so messages arrive in the order they were sent, also when both people dial at once: an accepted connection takes over only once the dial's task has the answers to what it sent, and a dial that is taken over goes on only reading. A dial lasts up to 15 s (`CONNECT_TIMEOUT`); one that failed is tried again a second later while the message is younger than 45 s, but only while a transfer with that person has a connection (`tries_again`, `Shared::connected_to`), since then the person is there and the transfers' data holds the dial up; a refusal, a side without chat and an address that cannot be found end it at once. `Command::Chat` ends as `Event::ChatSent` or `Event::ChatFailed` (no connection, refused, no answer to `Hello` within 20 s, no `Received` within 60 s, or the connection ended first), never both; `Command::Typing` is never answered, and after a dial that failed it dials that person again only after a minute. Nothing is kept for later: the user sends a failed message again.
- Who may write: `ChatPolicy` (`Config::chat_policy`: `Config::chat_from`, the recipients, the user's name), set with `NetHandle::set_chat` wherever `set_blocked` is called. A blocked sender, and with `ChatFrom::Recipients` anyone who is no recipient, gets `Refused` before anything is emitted, at `Hello` and at every `Text` and `Typing` after it, so blocking holds on a connection that is open. With `ChatFrom::Recipients`, a person whom a message of the user's reached may answer for 24 hours (`Chats::wrote_to`, `ANSWERS`, kept in memory): their answer would otherwise be refused like any message of theirs.
- History: `chat::History`, `<data_dir>\chats\<contact id>.json`, the newest 2000 messages (`{time, mine, text, failed}`), written by the user interface for what it shows. Later versions must keep reading these files. A message is in its chat as sent from the moment it is written, so the messages on their way are noted beside the chats (`chat::Sending`, `chats\sending.json`, which is there only while one is on its way): one that the program ends on is marked as not sent at the next start (`Sending::start`, before any chat is shown: `ui::chat::start` on Windows, `Chats::new` in the ffi).
- Windows: one modeless window per person (`App.chats`, by the Contact ID in lower case), opened with Ctrl+M, the recipient's menu, the Chat button of the Incoming and progress windows, and by a message that arrives (then without taking the focus). The history is an owner-drawn list box with `LBS_HASSTRINGS`, so that long messages wrap and screen readers still get each item's text; it is drawn by the window's `urgent` function (`chat::draw_history`), so it also shows while the window asks something. Its rows are the messages of `History::entries`, one for one. It takes several selected messages (`LBS_EXTENDEDSEL`; `chat::selected`, `select_only`): Ctrl+C copies them, Ctrl+A selects all and Delete deletes them from this computer after `confirm_no` (`History::remove`), each told in the status line; `history_proc` posts those keys as commands, so that the question's loop does not run inside the list, and the context menu (`Chat::history_menu`, with `ui::menu`) has the same three. A list item can be no higher than 255 pixels, so a box below the history has the whole text of the message that the user is at there (`Chat::show_selected`, by the focus rectangle, also among several selected; a `read_only_text`), and a user who reads there or in the history stays there when a message arrives (`Chat::reading`). The main window has a Chat… button beside Send File… and Send Folder…, without an access key, as the others. A message that arrives while the window is in front is announced through the status line, a live region, 300 ms after the last one (all that arrived together, as `incoming.rs` does); while it is not, the notification tells of it (`BalloonAction::Chat`), and never both. A message of the user's that arrived (`Event::ChatSent`) plays its sound, and the window in front announces it the same way, with the user's own name (`Config::my_name`) where the other person's has theirs, together with what arrived meanwhile (`Chat::delivered`); one that is not in front says nothing. "… is typing" is announced once when it begins, in the window in front (`Config::announce_typing`, which leaves the Typing sound to its own setting), and lapses after 8 s without another word; the user's own typing is told at most every 3 s (`Config::send_typing`). Messages on their way are in `chat::UNCONFIRMED` (a `chat::Sending`), not in the window, which may close first. With several boxes checked, Ctrl+M asks for one message (`chat::message_several`) and sends it to each person as a message of its own (`send_to_each`: through the chat window that is open, or into the chat on the disk), since the network knows only chats of two; it sends to all or, while one of their chat windows is busy, to nobody. The events have a lane per person (`app::Lane::Chat`); `Typing` has none.
- The Mac: `crates/dodavo-ffi/src/core/chat.rs` (under `cfg(target_os = "macos")`) holds what `ui/chat.rs` does on Windows: the `History` of each chat whose window is open, the messages on their way, who is typing (said once, lapsing after 8 s, by the 1 s tick) and the user's own typing (calls `chat_open`, `chat_closed`, `chat_send`, `chat_send_several`, `chat_typing`, `chat_delete`, `chat_delete_all`, `any_chats`). It tells Swift of a message that arrived, one of the user's that was added, one that failed and of typing (`Out::ChatMessage`, `ChatAdded`, `ChatFailed`, `ChatTyping`). Each change of an open chat has a number (`seq`), which `chat_open` gives too: a window that opens for a message has that message already, and leaves out what it is told of it. `ChatWindow.swift` is one window per person (`AppDelegate.chats`): the conversation is a table with one message per row, whose cell is one sentence to VoiceOver, and the window writes the times as the Mac does. A message that arrives opens the window without the focus; in front it is announced, 300 ms after the last one and never sooner than 2 s after the window became the key window, and otherwise its notification tells of it (`Notifier.Action.chat`), never both. Chat in the File menu (Shift-Command-M, since Command-M minimizes) goes down the responder chain as `chat:`, which the main window (the selected recipient, or one message for several through `messageSeveral`), the Transfers window (the selected row's other side) and the Incoming window (the sender) each take. There the Chat page of Settings has the three settings and Delete All Conversations….

### Updates (`src/update/`, `src/ui/update.rs`)

`update::mod` fetches the signed manifest from the fixed GitHub URL (`MANIFEST_URL`), verifies the Ed25519 signature (`keys.rs`, `statement.rs`) before trusting anything in it, compares versions (`version.rs`, hand-written semver) and downloads the installer while hashing it. A request that failed is told as a server that could not be reached or that did not answer in time (`Error::Network`, `Error::Timeout`), without the library's English words, and a file error in the system's words (`Error::io`). Each check or download runs on its own thread with a `current_thread` tokio runtime and reports `update::Event`s through `app::update_sink`; `App.update_job` identifies the current job, so cancelling is forgetting the job, and events of old jobs are dropped. `ui::update` owns the "Update Available" window (modeless, like the incoming window), the scheduler (`tick()`: 15 s after start, on going online, then hourly it checks whether 24 h have passed; `Config.check_updates`, `update_last_check`, `update_remind_after`) and the manual check. Installing: Setup is started with the plain `open` verb (never elevated by Dodavo) and `/VERYSILENT … /CURRENTUSER|/ALLUSERS /DODAVOUPDATE=<pid> /DODAVOARGS="--updated …"` (`update::install_mode` compares the exe folder with the HKCU/HKLM uninstall registrations). For all users Setup elevates itself (Windows asks). Its `InitializeSetup`, which runs in the elevated process, posts `Dodavo_ExitForUpdate` to every `Dodavo_Main` window and waits for the pid and the `Local\DodavoRunning` mutex; the main window's handler closes the instance mutexes (`main::release_instance_mutexes`) and exits (the installing instance as chosen in the window, `App.update_cancel_transfers`; other profiles with transfers suspended). Until then Dodavo keeps running and only watches whether Setup ended early (declined elevation → exit code 1 → error in the window). `PrepareToInstall` waits once more, and the second `[Run]` entry (`runasoriginaluser`) starts Dodavo again unelevated. The message name, the class name and the parameters are a contract between the program and every future installer. `manifest.rs`, `statement.rs`, `version.rs` and `keys.rs` are `#[path]`-included by the release tool, so they must not use `crate::` paths. Bumping `format` in the manifest makes old programs ignore it.

### Other modules

- `archive.rs`: folder zipping/unzipping, which rejects unsafe paths with its own check of the entry names (`entry_path`, `is_plain_name`, `is_device_name`: the zip crate's `enclosed_name` panics on ordinary names such as "Kuća.jpg" in zip 9.1 and 9.2). `unzip` creates only new files, so of two entries whose names collide (the same once case does not count) the later one gets a number (`open_unpacked`), and `unzip_within` stops at a size (see Size limit). It also provides `sanitize_file_name` (which shortens a name to 240 UTF-16 units on Windows, bytes elsewhere, so that `.zip.part` and a number still fit), `file_id`, `name_taken` (also true for a deleted file that is still open somewhere, which keeps its name and makes creating it fail with access denied) and the functions that take a free name in one step without ever replacing anything (`create_unique_file`, `create_unique_dir`, `move_to_unique`, `rename_new`); there is deliberately no "find a free name" function to use later. Any name coming from a peer must pass through these.
- `i18n/`: translations. `mod.rs` lists every key in the `strings!` macro; each language (`en.rs`, `hr.rs`, `sr_latn.rs`, `sl.rs`) is one `Strings` const, so a missing translation fails to compile. Use `tr!(key)` / `tr!(key, name = value)` for `{name}` placeholders and `trn!(key, n, …)` for number-dependent text (CLDR plural categories; Slovenian has a dual). Build sentences as whole strings per variant (no "file"/"folder" word splicing), and keep peer names out of positions that need grammatical case (use "– primatelj: {name}" or parentheses). Tests check placeholders and that access keys are unique per window/menu; add new controls with access keys to the groups in `access_keys_are_unique`. The language comes from `DODAVO_LANG`, then the `language` setting, then the Windows display language (English fallback), and is fixed for the process lifetime.
- License: Dodavo is GPL-3.0-or-later (`LICENSE`), © Hrvoje Katić; author, website and copyright years come from `Cargo.toml` (`ui::APP_AUTHOR`, `ui::APP_WEBSITE`, `ui::COPYRIGHT_YEARS`; see Commands → Installer). `ui/about.rs` is the About task dialog (website link via `TDN_HYPERLINK_CLICKED` → `shell::open_url`, License button); it shows the GPL's "Appropriate Legal Notices" (copyright, no warranty, the license and how to read it), so keep them when changing it. `ui/license.rs` is the modal License window: the built-in `LICENSE` and `res/third-party-licenses.txt`, chosen with a drop-down list. The license texts stay in English. Help → Donate opens `ui::DONATE_URL` in the browser (`about::open_link`). Setup deliberately has no Welcome and no license page (see the comment in `Dodavo.iss`) and installs both files next to the program.
- Help: `res/help/<lang code>.html` (one page per language, plus the shared `help.css`) is built in by `ui/help.rs`, written to `%TEMP%\Dodavo\help` and opened in the default browser in the current UI language (Help → View Help, or F1 in any window via `main_window::translate`). Pages follow WCAG 2.2: one `<h1>`, no skipped heading levels, landmarks, a skip link, `<kbd>` keys, and keyboard/screen reader instructions for every task. When you change a feature or a UI string, update all four pages. Tests check that the pages have identical ids and heading structure, that links resolve, and that they quote the program's current texts.
- `ui/send_to.rs` and File Explorer's menus: `shell::set_explorer_menu` writes "Send with Dodavo" for this user under `HKCU\Software\Classes\*\shell` and `Directory\shell`, and a shortcut in the Send to folder, at each start of the default profile of an installed copy (`explorer_menu_available`), so that they follow the path and the language; Setup only removes them (`[Registry]` with `dontcreatekey uninsdeletekey`, `[UninstallDelete]`; a test checks that it names them). They are classic entries, the same on Windows 7 to 11, which on Windows 11 sit under "Show more options": a top-level entry there takes a sparse package signed with a trusted certificate and a COM DLL (`TODO.md`). The verb is `MultiSelectModel=Player`, which shows it for up to 100 selected items and starts one process per item, also for a mix of files and folders; Send to starts one process with all of them. `main.rs` hands the paths to the running instance with `WM_COPYDATA` (`forward_to_running_instance`; it keeps no handle to the instance mutex, so that it cannot make a new start take itself for a second one, holds `Local\DodavoRunning` while it waits, since it keeps the program's file open, and takes over if the instance ends meanwhile), and `urgent_message` takes them, also while a dialog is open. That message can arrive during any call that waits for another thread, so it only notes them and posts `WM_APP_SEND_TO`. Paths and controls live in thread-locals, not in the handler, since more can arrive while Add Recipient is open, and not in `app::Queued`, whose busy events would hold up the network's. Nothing is sent until the user chooses Send, so `WM_COPYDATA` can only open this window. Each item is its own transfer, as with several dropped items.
- Blocked senders (`Config::blocked`, `block`, `unblock`): the network gets their IDs at start (`net::start`) and after every change of the settings (`NetHandle::set_blocked`, from `app::update_cfg` and the ffi's `save`), and `net::accept` answers their `Offer` with `Decline` before anything is emitted, so no window or notification sees it, and the protocol is unchanged; transfers with them that are under way go on. A recipient is never blocked: blocking removes the recipient, and `Config::add_contact`/`replace_contact`, which every place that adds or edits one uses, unblock. Windows blocks from the Incoming window (`incoming::decline_from` declines the sender's other waiting offers), the File and context menus, and unblocks in `ui/blocked.rs` (Settings → Blocked Senders…); the Mac from the same places, with the Settings tab Blocked (calls `block`, `unblock`, `blocked`).
- Size limit (`src/limit.rs`; `Config::limit_size`, `size_limit`, `over_limit`, `Contact::limit`): the largest item that someone may send, off by default, with a limit of a recipient's own coming before the general one (`Config::limit_for`), which also holds for senders who are not recipients. An item counts as the larger of `Offer.size` and `Offer.content_size` (`limit::over`), each item by itself. What happens to a larger one is `OverLimit`: `Ask` (the default) keeps it from starting by itself (`Config::auto_save_dir_for`, which Windows' `Event::Offer` and the ffi's `on_offer` both go by) and the Incoming window says so (`limit::notice`; `OfferOut.over_limit` for the Mac and Android); `Decline` and `DeclineAndTell` are the network's (`net::Limits`, set at `net::start` and by `NetHandle::set_limits` wherever `set_blocked` is called), which answers such an `Offer` with `Decline` in `net::accept` as for a blocked sender, and with `DeclineAndTell` emits `Event::OverLimit` (a balloon on Windows, `Out::Declined` for the Mac's and Android's notification). The protocol is unchanged, so the sender only sees a decline. With a limit for the sender, a folder is not unpacked past the larger of the limit, as it is at that moment, and what the offer said (`Receiver::unpack_max`, `archive::unzip_within`, `error_folder_too_large`). Without a limit it is held to the larger of what the offer said and what its zip states, and a zip that states more than the offer (a file that grew while it was packed, or a sender whose program says less than it packs) is unpacked only where there is room for all of it (`unzip_within`'s `offered`). The settings take a whole number of MB or GB (`limit::from_input`, `to_input`, 1024-based as `format_size`), the same way on all three (`LimitSettings` and `RecipientLimit` in the ffi, which also lists the recipients with their limits). A `Contact` without a limit of its own is written as before, so earlier versions' files and blocked entries stay as they were.
- Sounds (`src/sound.rs`; `ui/sound.rs` on Windows, `Sounds.swift` on a Mac; Android: `TODO.md`): `sound::SoundEvent` lists the events that have one (`ALL`, in the order of the settings; `key` names an event in the settings file and must not change) with the built-in WAV of each, and `Config::sounds` (`config::Sounds`: `on`, and per event `SoundChoice::Default`, `Off` or `File`) what the user chose; an event that the file names and this version does not know is kept. `ui::sound::play` plays with `PlaySoundW` (winmm, on Windows 7 too), one sound at a time, and a file that cannot be played gives the built-in sound. The transfers' sounds are played in `app.rs`, where the state tells whether the event was handled before (an event that finds its window busy comes again): `Incoming` at an offer, `Started` at the user's send or accept, `ConnectionLost` and `Continues` by `sound::phase_sound`, and the end by `sound::outcome_sound`, once (`Transfer::active`). A notification that follows one of Dodavo's sounds within half a second leaves out Windows' own (`sound::just_played`, `NIIF_NOSOUND`). Settings → Sounds sets them (`settings.rs`), and Play there works while sounds are off. On a Mac the ffi decides at the same moments (`Core::sound`) and tells Swift what to play (`Out::Sound`, pushed before the notice of the same event), `Sounds.swift` plays it with `NSSound` (any sound file that macOS plays can take a built-in sound's place, so `sound_not_playable` and the open panel speak of sound files, not of WAV), and `Notifier.post` leaves out the notification's own sound after one (`Sounds.justPlayed`). Its Sounds page (`SoundSettings.swift`; calls `sounds`, `set_sounds_on`, `set_sound`, `reset_sounds`, `try_sound`) applies each change at once, with the file chosen through Choose… in the pop-up menu.
- Change My Contact ID (Windows and the Mac; Android has none): `NetHandle::change_identity` (`Command::NewIdentity`) gives the installation a new key without a restart. No transfer can go on under another identity (`net::accept` takes `Continue` and `Query` only from the peer a transfer began with), so the network thread first stops taking connections, declines every waiting offer and cancels every transfer (`end_all_transfers`), which the peers learn through the old endpoint, and each transfer reports its `Finished` as after any cancel. If one is left after 5 s (a send whose cancel waits for the receiver's verdict, or one handed over), it answers `IdentityError::Busy` and nothing changes. Otherwise `identity::replace` writes `secret.key.new` and renames it over `secret.key` (a crash leaves a whole key; `load_or_create` removes a leftover), and only then the old endpoint is closed and a new one bound, in the same runtime, with the same `Shared`, sink and blocked set. The answer is sent once the key is on the disk. Windows: `app::change_contact_id` (File menu and the Change… button in Settings, which has no access key, as it is not something to reach by accident), with `ui::confirm_no` and `incoming::decline_all`; it blocks the UI thread while it waits. The Mac: the call `change_contact_id` (`{error, my_id, declined}`), `AppDelegate.changeMyContactID`; `Core.my_id` and `AppDelegate.myId` hold the current ID (`Started.my_id` is the one at the start). The block shortcut is Ctrl+B and Command-B (also on Block Sender in the Mac's Incoming window).
- Several recipients at once: an item to several people is a transfer of its own for each, so the protocol and the network know nothing of it. Windows: both recipient lists have check boxes (`LVS_EX_CHECKBOXES`, `main_window::list_checked`), and a send goes to the checked recipients, or to the selected one when none is checked (`MainWindow::recipients`, `SendTo::send`, both through `app::start_sends`, which starts nothing if one Contact ID is not valid); the file dialog's title and the drop question name them, a drop on an unchecked row is for that one alone, and the boxes are cleared once a send started. Edit, Remove and Block stay with the selected row. The Mac: the table's own multiple selection (`targetContacts`; VoiceOver selects with VO-Command-Return), with Edit, Remove and Block for exactly one, and a list in the question for items from the Dock and Services (`RecipientPicker`). Android: a selection mode on the Recipients screen and on the share screen (`RecipientListItem`, `SelectionTopBar`), started by a long press, which accessibility services offer as an action, and by Select in the row's menu or the top bar. The ffi's `send` and `send_documents` take `peer_ids` and start nothing unless every one is a recipient; a staged copy belongs to one transfer, so Kotlin makes one for each recipient (`Sending.sendFiles`).
- Several items at once: each is its own transfer, on both sides. The Incoming window holds all of one sender's waiting offers, with one answer (`incoming::open_or_add`), because windows of their own would open exactly on top of each other, and a user who answers the one in front leaves the others waiting unseen. An offer that arrives while that window has a dialog open gets a window of its own rather than hold up the queue. Accept covers what can have been seen: what arrived within the last second stays in the window (`split_seen`). The Mac does the same in `IncomingWindowController` (`takes`, `add`, `remove`, `seen`; `AppDelegate.showOffer` gives a window of its own a place beside the others): the window asks the bridge what to say of its offers (the call `offers`, and `space`, `check_accept` and `accept` with `ids`), says an added one aloud when it is the key window and leaves that to the notification otherwise. Android shows one offer at a time. The free space is checked for an offer, or for the offers of a window together, beside what the receives under way still have to write, which the disk does not show yet (`space::Arriving`; `app::arriving` on Windows, `State::arriving` in the ffi), so that items which fit one by one do not all start by themselves, and the text says what takes the room (`space_arriving_note`). When its transfer ends, a progress window stays and shows the result, with Open the file and Open the folder (or Open the folder alone) after a receive, which close it too; there is no question or message at the end. Its status line and the line below are live regions, read once when the window is in front, and a notification tells of the end otherwise, never both. With `Config.close_when_ended` (Windows only, off by default), which the check box of every progress window and Settings → Transfers share (`progress::set_close_at_end`; Settings writes it only when its box was changed there), every window closes as soon as its transfer ends, also one that failed, was declined or was cancelled, with a notification. A window in the background closes in any case, and so does a minimized one whose transfer completed (`progress::at_end`).
- `config.rs`: JSON settings and contacts in `%APPDATA%\Dodavo[\profile]`, including migration from the old `QuickAndEasyFileTransfer` folder. Every field is saved, so a file cannot tell a choice from a default of its time: when a setting changes its meaning or its default for those who have it, raise `SETTINGS_VERSION` and handle the old file in `Config::upgrade`. A file of 1.0.0 has no version, and its cleared `always_save` with `auto_accept` becomes the box on with Downloads, which is where those transfers went; a cleared box now means that Dodavo asks where to save every item (`Config::auto_save_dir`). Version 2 drops the message after a send and the question after a receive (`show_after_send` and `ask_after_receive`, read from older files and never written): a file that had both cleared gets `close_when_ended`, since its windows closed at the end. The Mac shares all of this. A damaged `config.json` is moved aside (`config.json.bad`) and reported at startup rather than silently replaced. The folder for temporary files (`Config::temp_dir`, Windows and the Mac; Android's folders are the app's) is the system's place unless the user chooses one in Settings: Dodavo then keeps its temporary archives in `<chosen>/Dodavo[/profiles/<profile>]` (`temp_dir_for`), never in the chosen folder itself, since a start deletes old archives from its temporary folder. The network takes it at the start (`net::TempDirs`) and after every change (`NetHandle::set_temp_dir`, where `set_blocked` is called), for the transfers that start from then on; a transfer falls back on the system's place while the chosen folder cannot be made (`Shared::temp_dir_now`). Folders chosen before stay in `temp_dirs_before`, and a start clears leftovers there too, until none are left (`forget_temp_dirs`). The update's download, the help pages and the copies of shared items stay in the system's place. A temporary archive of 4 GiB or more fails on FAT32, so with `Config::warn_fat_temp` (Windows and the Mac, on by default) the user is asked first, and can choose another folder, go on or cancel, with a check box that turns the setting off: before a send, for a folder whose files are that large together where its zip would be packed on FAT32 (`space::send_temp_warning`, by the rule of `send::pack_in`; `app::start_sends` → `may_pack` on Windows, the call `check_send` in `MainWindow.start` on the Mac), and before a receive whose zip goes to the temporary folder (`session::part_in_temp`) when that is on FAT32 too (`Space::temp_warning`; `Incoming::accept` on Windows, `check_accept` with `temp_warning` and `ignore_temp` on the Mac), which also keeps such an offer from starting by itself. Windows asks with `app::ask_about_temp`, the Mac with `warnAboutTempFolder` (`Speech.swift`, with the calls `set_temp_dir` and `warn_fat_temp`). Android never warns: its archives are in the app's own storage. `identity.rs` stores the secret key there and refuses to overwrite an existing but unreadable or damaged `secret.key`.
- `ui/window.rs`: a small framework over raw Win32. Each window owns a `Handler` trait object. Control rects are in 96-DPI units and scaled automatically. It handles fonts, DPI changes, theming, and modal loops (`run_modal`). While a handler is borrowed (it opened a modal window, message box or task dialog), messages to its window skip it; messages that must not be lost and need no handler state go through `CreateOptions::urgent` (the main window's `urgent_message`: `Dodavo_ExitForUpdate`, end session, `TaskbarCreated`). Framework windows have no owner, so destroying the main window does not close a `run_modal` window: `main_window::exit` posts `WM_QUIT` at once, which ends every open dialog loop (`run_modal` then closes its window). `Window::text_height` measures wrapped label text, which follows the Windows text size (DPI scaling alone does not). Use `with_handler::<T>` to reach a window's handler from outside. New dialogs should follow the existing ones (`settings.rs`, `recipient.rs`, `incoming.rs`). A window with pages has a row of tabs (`Window::tabs`, a `SysTabControl32` only as high as its tabs) and keeps the controls of every page as its own children, showing one page's at a time (`settings.rs`: General, Transfers, Receiving, Chat, Sounds), so hidden controls take neither Tab nor an access key, and access keys need to be unique only within a page; Ctrl+Tab and Ctrl+Page Down/Up change the tab from anywhere (`window::switch_tab`, called by `main_window::translate`), and `theme::tabs_subclass` draws the row in dark mode. The per-monitor DPI functions (Windows 10 1607) are looked up at run time in `dpi_api()` with system-DPI fallbacks.
- `ui/main_window.rs::translate` does accelerators and Tab navigation (`IsDialogMessageW`) for the main loop. `ui/menu.rs` has the helpers for menus made in code (the menu bar and the context menus).
- `ui/theme.rs`: light/dark handling for the title bar, menus and controls. `ui/tray.rs`: the notification-area icon and balloons. `ui/shell.rs`: shell integration (Start with Windows, etc.).
- Single instance per profile through a named mutex. A second launch posts `show_message_id()` to the existing main window. Every instance also holds `Local\DodavoRunning`, which Setup and the uninstaller wait for after asking every instance to exit with `Dodavo_ExitForUpdate` (with a `wParam` of 1, which suspends all transfers, where an automatic update's 0 does as the user chose in the Update Available window; `PrepareToInstall`, `CurUninstallStepChanged` at `usAppMutexCheck`, which comes after the user confirmed). `Dodavo.iss` deliberately has no `AppMutex`: Inno checks it at Setup's start and would ask the user to close Dodavo before the wizard. Keep both names in step.
- `installer/`: `Dodavo.iss` (per-user by default, fixed `AppId`, never change it), `build.ps1`, and `languages/` with adapted Croatian and Serbian (Latin) Inno Setup translations (formal address, Windows terms). Setup must offer the same languages as `src/i18n`. When you add a language, add its `.isl` (official or vendored and reviewed) to `[Languages]`. The help's "Installing and uninstalling" section quotes Setup's texts.

Win32 calls mostly use `windows-sys`. The `windows` crate is used only for COM shell APIs. Strings go through `ui::wide` / `ui::from_wide_ptr`.

## Guidelines

- **Branches.** `master` holds stable code and `dev` is where development goes on. Work on `dev`, or on a branch of its own, made from `dev`, for a feature or for support of a new platform. Such a branch always ends up in `dev` once the feature is done, and is then deleted, locally and on GitHub. Nothing is committed to `master` directly: it takes what is in `dev`, and only when the user asks for that. CI runs on every push to `master` and `dev`; another branch gets it through a pull request.
- **Known issues and the to-do list.** `ISSUES.md` lists what is wrong now and `TODO.md` what still has to be done, each sorted by priority (High, Medium, Low). Read both every time you review code. Report a finding that is already listed as known, not as new; check whether the code under review fixes, worsens or touches a listed item; and add what a review finds and does not fix right away, under the priority it deserves. Remove an item in the commit that settles it. Both files are public, so keep secrets and private addresses or paths out of them, and write plain tasks and facts: what to do, not what nobody has done yet.
- **macOS 11 is the oldest supported macOS.** It cannot be run in a virtual machine here (they start at macOS 12). Guard Swift APIs newer than it with `if #available`, which the compiler enforces, and keep `macos/check-floor.sh` passing. Apple's tools may stop taking this target; then the floor has to move.
- **Android 8.0 (API 26) is the oldest supported Android.** Guard Kotlin APIs newer than it with `Build.VERSION.SDK_INT` (lint reports what is not), call Linux system calls that Android 8 to 10 filter only on API 30 and later, and run the core's tests (`android/test-on-device.sh`) and the screens on an API 26 emulator after changing either.
- **Windows 7 SP1 is the oldest supported Windows.** Never import a Win32 function statically that is newer than Windows 7 SP1 (for example the `*ForDpi` functions, `SetThreadDescription`, anything in `combase.dll`, `shcore.dll` or an `l1-2-*` API set): the loader then refuses to start the program on older Windows. Resolve it with `GetModuleHandleW`/`GetProcAddress` and fall back (pattern: `dpi_api()` in `ui/window.rs`, `api()` in `ui/theme.rs`), and avoid `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_SYSTEM32` for anything that must work on an unpatched Windows 7. The `windows`/`windows-sys` crates bind some functions to Windows 8 DLLs (`CoTaskMemFree` → `combase.dll`); declare those yourself against the old DLL, as `platform/windows.rs` does. The first library on the linker's command line wins for the whole program, also for the calls in those crates, so the program itself has to name it (`#[link(name = "ole32")]` in `main.rs`): the library's own comes too late. Stable Rust itself only supports Windows 10+, so the Windows 7 builds use the Tier 3 win7 targets (see Commands). After changing Win32 calls or dependencies, run `installer\check-imports.ps1` on the release exe. Structs like `NOTIFYICONDATAW` are packed on 32-bit: don't take references to their fields.
- **Avoid `unsafe`.** Use it only when there is no safe alternative, which in practice means direct Win32/FFI calls. Keep each `unsafe` block as small as possible, and prefer safe wrappers (for example, the helpers in `ui/mod.rs` and `ui/window.rs`) or safe crate APIs over new raw calls.
- **Accessibility is a high priority.** Every feature must work fully with screen readers (NVDA, JAWS, Narrator, VoiceOver, TalkBack) and with the keyboard alone:
  - Every control needs an accessible name. Put a visible label right before it in creation order, or set the name explicitly.
  - Tab order must be logical, Enter and Escape must work, and menu items need access keys and shortcuts.
  - Status changes such as progress, completion and errors must be perceivable without seeing the screen.
  - Don't rely on color alone. Owner-drawn or custom-themed controls must keep working with assistive technology.
- **User documents.** The help pages and the README say what the program needs and does, and only what is true of it. Nothing about what was or was not tested, nothing from the making of it, and no warnings that do not help the reader do something: users take those as a reason not to use it. Check a claim against the code or a real run before writing it. What is left to try goes in `TODO.md`. The GPL's notices stay.
- **Localization.** Whenever you add or change a user-facing string, update the translations for every supported language in the same change. Never leave a language behind or fall back to English. When adding a new language, or translating into any language, check terminology, grammar and style against trusted sources for that language. Examples are official language institutes and dictionaries, and the Microsoft Terminology/Language Portal for Windows UI terms. Use Windows' own established terms for that language (for example "Downloads", "notification area", "Settings") so the app is consistent with the system.
