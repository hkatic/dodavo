# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dodavo is a Windows-only Rust app (classic Win32 UI) for sending files and folders directly between computers over [iroh](https://iroh.computer). Peers are identified by a permanent **Contact ID** (the iroh public key), not an IP address. See README.md for the user-facing feature list.

## Commands

- Build: `cargo build --release` → `target\release\Dodavo.exe`. Needs the MSVC toolchain and Windows SDK (`rc.exe`); `build.rs` embeds `res/app.rc`, `res/app.manifest` and `res/app.ico` via `embed-resource`. `.cargo/config.toml` links the C runtime statically for every target. 32-bit: `cargo build --target i686-pc-windows-msvc`.
- Installer: `powershell -ExecutionPolicy Bypass -File installer\build.ps1` → `target\installer\Dodavo-<version>-setup.exe` + `.sha256`. Needs Inno Setup 6.6+ (32-bit edition). It builds four programs: x64 and x86 with stable Rust for Windows 10+, and x64 and x86 for Windows 7 SP1–8.1 with the Tier 3 `*-win7-windows-msvc` targets on a nightly pinned in `build.ps1` (`-Zbuild-std`, own `target\win7` dir). `-SkipWin7` builds a Windows 10-only installer. Setup picks the build by Windows version and install mode (`[Files]` in `Dodavo.iss`). Signs with signtool when `DODAVO_SIGN_THUMBPRINT` or `DODAVO_SIGN_PFX` is set (see README). The version comes from `Cargo.toml` (`build.rs` passes it to `res/app.rc`); `res/app.manifest` repeats it by hand, and `build.rs` fails when the two differ.
- Third-party licenses: `powershell -ExecutionPolicy Bypass -File installer\licenses.ps1` regenerates `res\third-party-licenses.txt` with cargo-about (`cargo install cargo-about --locked --features cli`; config `installer\about.toml`, template `installer\about.hbs`). `build.ps1` runs it first. Run it after adding or updating dependencies and commit the file with `Cargo.lock`; a new license must be GPL-3.0-compatible before it goes into `accepted`.
- Publish: `powershell -ExecutionPolicy Bypass -File installer\publish.ps1 [-Publish]` writes and verifies `target\installer\update.json` (the signed update manifest) from the built installer, `release-notes\<version>\<lang>.txt` and the secret key in `DODAVO_UPDATE_KEY_FILE`, and with `-Publish` creates the GitHub release `v<version>` through `gh`. The release tool behind it: `cargo build --release --features release-tool --bin dodavo-release` (`keygen`, `manifest`, `verify`). The private release guide lives outside the repo (`C:\Users\hrvoj\Documents\Dodavo-release\RELEASING.md`).
- Import check: `powershell -ExecutionPolicy Bypass -File installer\check-imports.ps1 <exe> [-Profile win7]` fails when an exe imports a DLL or function newer than its Windows baseline. `build.ps1` runs it on every build; run it after touching Win32 calls or dependencies.
- Test everything: `cargo test`
- Single test: `cargo test <name>`, e.g. `cargo test end_to_end` or `cargo test archive::`
- `net::tests::end_to_end`, `resume_after_disconnect` and `resume_after_restart` start two real iroh endpoints in one process and need internet access (address lookup / relays). Run them with `--test-threads=1`; each can take a minute or two.
- Run two instances side by side: `Dodavo.exe --profile alice` and `Dodavo.exe --profile bob` (separate identity and settings). `--minimized` starts in the tray.
- Update testing: `DODAVO_UPDATE_URL` overrides the manifest URL (a local `python -m http.server` works) and `DODAVO_UPDATE_KEY` the trusted public keys (hex). `--updated` is what Setup starts the program with after an update.
- Force theme for testing: set `DODAVO_THEME=dark` or `DODAVO_THEME=light`. Force language: `DODAVO_LANG=en|hr|sr-Latn|sl`. `DODAVO_LEGACY_DPI=1` uses the Windows 7/8 DPI code path (system DPI only) on a current Windows.
- Debug builds keep a console window; release builds use the `windows` subsystem. A panic hook shows a message box.

## Architecture

Two threads that never share UI state:

1. **UI thread** (`main.rs` message loop): owns all windows and the `App` state in `app.rs`, stored in a `thread_local!`. Access it only through `app::with(|a| …)`; do not create windows or show message boxes inside that closure, because they run nested message loops and would re-borrow the `RefCell`.
2. **Network thread** (`net::start`): a tokio multi-thread runtime that owns the iroh `Endpoint`.

They communicate in two directions:
- UI → net: `net::Command` (`Send`, `Respond`, `Cancel`) over an unbounded mpsc channel (`app::net_send`).
- net → UI: `net::Event` is pushed by `app::event_sink` into a global `EVENTS` queue (as `app::Queued::Net`; the update thread pushes `update::Event` through `app::update_sink` as `Queued::Update`), which then posts `WM_APP_NET` to the main window. `app::process_events` drains the queue on the UI thread. If a target window is busy (for example, a modal message box is open), the handler returns the event, which is requeued and retried after 250 ms by a timer. Keep that contract when adding events. `Progress` events may be dropped; the others must not be.

Transfer ids come from `net::next_transfer_id()` and are used in both directions (restored transfers get fresh ids). `App.transfers` maps id to progress window, and `App.offers` maps id to incoming-offer window. The progress window (`ui/progress.rs`) has Pause/Resume, Minimize to background and Cancel; a lost connection shows a question after 3 s unless `Config.connection_lost` decides, and phase changes may return a notification (`PhaseNotice`) because label changes are not announced by screen readers.

### Networking (`src/net/`)

- `protocol.rs`: ALPN `dodavo/2`. Every connection carries one bidirectional stream. A transfer is identified by a random 16-byte token in the `Offer` and may span several connections: `Offer` → `Accept|Decline` → `Data{len}` frames of raw bytes (≤ 256 KiB) → `Done{blake3 hash}` → `Result`; on a later connection the sender sends `Continue{token}` and the receiver answers `ContinueFrom{have}` (or `Gone`). `Paused`/`Resumed` may be sent by either side between frames; the receiver can ask `Query{token}` → `Alive|Gone`. Control messages are postcard-encoded with a u32 LE length prefix, capped at 64 KiB. There is no public release yet, so `Msg`/`Offer` may still change freely; once Dodavo is released, a change to them must bump the ALPN, because it breaks existing installs.
- `session.rs`: `TransferRecord` (JSON in `<data_dir>\transfers\<token>.json`, written once a transfer is accepted and deleted when it ends) lets a transfer continue after a lost connection or a restart; `net::start` restores the records at startup (`Event::Restored`). A tombstone `<token>.gone` is left when a side ends a transfer while the other side is away, so `Continue`/`Query` get `Gone`. Both are forgotten after 30 days. `Session` (per running transfer) routes a new connection to its task and holds the current connection; `Control` carries the cancel token and the pause flag (`watch`). Integrity stays one blake3 over the whole stream: the sender keeps hash snapshots every 64 MiB (`Snapshots`) and re-hashes the rest of the prefix with `hash_range`; the receiver re-hashes its `.part` after a restart (`Phase::Verifying`).
- `send.rs` / `receive.rs`: one task per transfer. The sender dials (with backoff) whenever the connection is lost; the receiver waits for `Continue` and queries the sender every 30 s. The receiver parks a `oneshot` in `Shared.pending` until the UI answers with `Command::Respond`. The sender's loop `select!`s between writing a frame (`SendStream::write` is cancel safe) and the receiver's messages; the receiver reads sequentially and lets a separate task own the `SendStream`. Close codes: `CLOSE_CANCELLED` (peer reports `CancelledByPeer`), `CLOSE_FAILED` (peer reports a failure), `CLOSE_SUSPENDED` (exiting or replacing the connection: peer treats it as lost and waits). Anything else, including timeouts, is a lost connection (`session::Lost`), never a failure. A checksum mismatch is reported over the stream (`Result{ok:false}`) and the connection is left open until the sender has read it. `Command::Shutdown` suspends transfers instead of cancelling them; the UI sends `Cancel` first when the user chooses to.
- Received files are written as `<name>.part` and renamed at the end. Folders are received as a temp zip (`recv-<token>.zip`) and extracted into a unique destination; sent folders are zipped to `send-<token>.zip`. Partial output is kept while a transfer can continue and removed by `Session::end` when it ends.
- `bind()` in `net/mod.rs` configures the endpoint (n0 preset relays + mDNS). This is where a self-hosted relay would be configured.

### Updates (`src/update/`, `src/ui/update.rs`)

`update::mod` fetches the signed manifest from the fixed GitHub URL (`MANIFEST_URL`), verifies the Ed25519 signature (`keys.rs`, `statement.rs`) before trusting anything in it, compares versions (`version.rs`, hand-written semver) and downloads the installer while hashing it. Each check or download runs on its own thread with a `current_thread` tokio runtime and reports `update::Event`s through `app::update_sink`; `App.update_job` identifies the current job, so cancelling is forgetting the job, and events of old jobs are dropped. `ui::update` owns the "Update Available" window (modeless, like the incoming window), the scheduler (`tick()`: 15 s after start, then hourly it checks whether 24 h have passed; `Config.check_updates`, `update_last_check`, `update_remind_after`) and the manual check. Installing: Setup is started with the plain `open` verb (never elevated by Dodavo) and `/VERYSILENT … /CURRENTUSER|/ALLUSERS /DODAVOUPDATE=<pid> /DODAVOARGS="--updated …"` (`update::install_mode` compares the exe folder with the HKCU/HKLM uninstall registrations). For all users Setup elevates itself (Windows asks). Its `InitializeSetup`, which runs in the elevated process before Inno's own AppMutex check, posts `Dodavo_ExitForUpdate` to every `Dodavo_Main` window and waits for the pid and the `Local\DodavoRunning` mutex; the main window's handler closes the instance mutexes (`main::release_instance_mutexes`) and exits (the installing instance as chosen in the window, `App.update_cancel_transfers`; other profiles with transfers suspended). Until then Dodavo keeps running and only watches whether Setup ended early (declined elevation → exit code 1 → error in the window). `PrepareToInstall` waits once more, and the second `[Run]` entry (`runasoriginaluser`) starts Dodavo again unelevated. The message name, the class name and the parameters are a contract between the program and every future installer. `manifest.rs`, `statement.rs`, `version.rs` and `keys.rs` are `#[path]`-included by the release tool, so they must not use `crate::` paths. Bumping `format` in the manifest makes old programs ignore it.

### Other modules

- `archive.rs`: folder zipping/unzipping, which rejects unsafe paths. It also provides `sanitize_file_name` and `unique_path`. Any name coming from a peer must pass through these.
- `i18n/`: translations. `mod.rs` lists every key in the `strings!` macro; each language (`en.rs`, `hr.rs`, `sr_latn.rs`, `sl.rs`) is one `Strings` const, so a missing translation fails to compile. Use `tr!(key)` / `tr!(key, name = value)` for `{name}` placeholders and `trn!(key, n, …)` for number-dependent text (CLDR plural categories; Slovenian has a dual). Build sentences as whole strings per variant (no "file"/"folder" word splicing), and keep peer names out of positions that need grammatical case (use "– primatelj: {name}" or parentheses). Tests check placeholders and that access keys are unique per window/menu; add new controls with access keys to the groups in `access_keys_are_unique`. The language comes from `DODAVO_LANG`, then the `language` setting, then the Windows display language (English fallback), and is fixed for the process lifetime.
- License: Dodavo is GPL-3.0-or-later (`LICENSE`), © Hrvoje Katić; author and website come from `Cargo.toml` (`authors` and `repository`: `ui::APP_AUTHOR`, `ui::APP_WEBSITE`), the copyright year is `ui::COPYRIGHT_YEARS` and is repeated in `res/app.rc` and `Dodavo.iss`. `ui/about.rs` is the About task dialog (website link via `TDN_HYPERLINK_CLICKED` → `shell::open_url`, License button); it shows the GPL's "Appropriate Legal Notices" (copyright, no warranty, the license and how to read it), so keep them when changing it. `ui/license.rs` is the modal License window: the built-in `LICENSE` and `res/third-party-licenses.txt`, chosen with a drop-down list. The license texts stay in English. Setup deliberately has no Welcome and no license page (see the comment in `Dodavo.iss`) and installs both files next to the program.
- Help: `res/help/<lang code>.html` (one page per language, plus the shared `help.css`) is built in by `ui/help.rs`, written to `%TEMP%\Dodavo\help` and opened in the default browser in the current UI language (Help → View Help, or F1 in any window via `main_window::translate`). Pages follow WCAG 2.2: one `<h1>`, no skipped heading levels, landmarks, a skip link, `<kbd>` keys, and keyboard/screen reader instructions for every task. When you change a feature or a UI string, update all four pages. Tests check that the pages have identical ids and heading structure, that links resolve, and that they quote the program's current texts.
- `config.rs`: JSON settings and contacts in `%APPDATA%\Dodavo[\profile]`, including migration from the old `QuickAndEasyFileTransfer` folder. A damaged `config.json` is moved aside (`config.json.bad`) and reported at startup rather than silently replaced. `identity.rs` stores the secret key there and refuses to overwrite an existing but unreadable or damaged `secret.key`.
- `ui/window.rs`: a small framework over raw Win32. Each window owns a `Handler` trait object. Control rects are in 96-DPI units and scaled automatically. It handles fonts, DPI changes, theming, and modal loops (`run_modal`). Use `with_handler::<T>` to reach a window's handler from outside. New dialogs should follow the existing ones (`settings.rs`, `recipient.rs`, `incoming.rs`). The per-monitor DPI functions (Windows 10 1607) are looked up at run time in `dpi_api()` with system-DPI fallbacks.
- `ui/main_window.rs::translate` does accelerators and Tab navigation (`IsDialogMessageW`) for the main loop.
- `ui/theme.rs`: light/dark handling for the title bar, menus and controls. `ui/tray.rs`: the notification-area icon and balloons. `ui/shell.rs`: shell integration (Start with Windows, etc.).
- Single instance per profile through a named mutex. A second launch posts `show_message_id()` to the existing main window. Every instance also holds `Local\DodavoRunning`, which is the installer's `AppMutex`; keep both names in step.
- `installer/`: `Dodavo.iss` (per-user by default, fixed `AppId`, never change it), `build.ps1`, and `languages/` with adapted Croatian and Serbian (Latin) Inno Setup translations (formal address, Windows terms). Setup must offer the same languages as `src/i18n`. When you add a language, add its `.isl` (official or vendored and reviewed) to `[Languages]`. The help's "Installing and uninstalling" section quotes Setup's texts.

Win32 calls mostly use `windows-sys`. The `windows` crate is used only for COM shell APIs. Strings go through `ui::wide` / `ui::from_wide_ptr`.

## Guidelines

- **Windows 7 SP1 is the oldest supported Windows.** Never import a Win32 function statically that is newer than Windows 7 SP1 (for example the `*ForDpi` functions, `SetThreadDescription`, anything in `combase.dll`, `shcore.dll` or an `l1-2-*` API set): the loader then refuses to start the program on older Windows. Resolve it with `GetModuleHandleW`/`GetProcAddress` and fall back (pattern: `dpi_api()` in `ui/window.rs`, `api()` in `ui/theme.rs`), and avoid `LoadLibraryExW` with `LOAD_LIBRARY_SEARCH_SYSTEM32` for anything that must work on an unpatched Windows 7. The `windows`/`windows-sys` crates bind some functions to Windows 8 DLLs (`CoTaskMemFree` → `combase.dll`); declare those yourself against the old DLL, as `ui/shell.rs` does. Stable Rust itself only supports Windows 10+, so the Windows 7 builds use the Tier 3 win7 targets (see Commands). After changing Win32 calls or dependencies, run `installer\check-imports.ps1` on the release exe. Structs like `NOTIFYICONDATAW` are packed on 32-bit: don't take references to their fields.
- **Avoid `unsafe`.** Use it only when there is no safe alternative, which in practice means direct Win32/FFI calls. Keep each `unsafe` block as small as possible, and prefer safe wrappers (for example, the helpers in `ui/mod.rs` and `ui/window.rs`) or safe crate APIs over new raw calls.
- **Accessibility is a high priority.** Every feature must work fully with screen readers (NVDA, JAWS, Narrator) and with the keyboard alone:
  - Every control needs an accessible name. Put a visible label right before it in creation order, or set the name explicitly.
  - Tab order must be logical, Enter and Escape must work, and menu items need access keys and shortcuts.
  - Status changes such as progress, completion and errors must be perceivable without seeing the screen.
  - Don't rely on color alone. Owner-drawn or custom-themed controls must keep working with assistive technology.
- **Localization.** Whenever you add or change a user-facing string, update the translations for every supported language in the same change. Never leave a language behind or fall back to English. When adding a new language, or translating into any language, check terminology, grammar and style against trusted sources for that language. Examples are official language institutes and dictionaries, and the Microsoft Terminology/Language Portal for Windows UI terms. Use Windows' own established terms for that language (for example "Downloads", "notification area", "Settings") so the app is consistent with the system.
